## 注释语法

工坊有三种注释写法，各有位置限制：

| 写法 | 可用位置 | 限制 |
|------|----------|------|
| `// 注释` | 规则体内、动作/条件块内、文件顶层 | **不能**放在规则名与花括号之间（`规则("X")` 和 `{` 之间） |
| `"注释"` | 仅限 `动作` 和 `条件` 块内，写在某条动作/条件**上方** | 不能用于规则外层结构 |
| `/* 注释 */` | 同 `"注释"`，仅限 `动作` 和 `条件` 块内 | 不能用于规则外层结构 |

```ow
// ❌ 错误：// 注释不能放在规则名和 { 之间
规则("示例")
// 这里不能放注释
{
    事件 { 持续 - 全局; }
}

// ✅ 正确：动作块内三种注释均可
规则("示例")
{
    事件 { 持续 - 全局; }
    动作
    {
        // 这是正确的行注释
        "匿名字符串注释"
        /* 块注释 */
        If(全局.X == 1);
            全局.Y = 2;
        End;
    }
}
```

## 调试工作流

用户反馈代码报错或不生效时，**第二次修改起**必须在关键节点加入 `记入查看器` 探针输出，并把所有需要用户反馈的内容统一记入查看器，让用户导入后直接复制查看器内容回传，再根据记录定位问题，不得盲目猜测并连续修改：

```ow
// 在怀疑的执行点插入：
记入查看器(自定义字符串("[TAG] 变量A={0} 变量B={1}", 全局.A, 事件玩家.B));
```

- 标签（如 `[1]`、`[S_Open]`）帮助区分多条消息的来源
- 每次只加 2-3 个探针，覆盖"触发是否到达"→"关键变量值"→"执行是否完成"三个节点
- 所有需要反馈的状态、分支结果和关键变量，统一记入查看器，方便用户一次复制完整记录
- 用户反馈查看器内容后再分析，不要在没有输出结果前连续推测修改

当你**不确定某种写法、函数组合、参数形式或工坊行为本身是否可用**时，不要直接把猜测写进用户主文件并连续改动；应先做一个**最小可验证测试**，再让用户反馈测试结果：

- 优先做**单条规则级**测试：只保留验证该写法所需的最少事件、条件和动作
- 若怀疑问题与其他系统叠加有关，再做**空模式 / 隔离模式**测试，把待验证规则放进最小环境中单独导入，并把测试反馈统一记入查看器
- 优先新建**独立测试文件**承载这些实验规则，不要先把实验性开关或半成品逻辑塞回主文件
- 测试目标要单一：一次只验证“这写法能不能导入 / 会不会执行 / 是否按预期生效”中的一个问题
- 若验证的是输入 / 密码 / 按键流程，至少让用户通过查看器反馈：**能否导入、正确路径是否成功、错误路径是否失败、长按是否重复触发**
- 用户反馈“能导入 / 不能导入 / 实际表现”后，再决定是否合并回主文件；若有查看器记录，优先让用户直接粘贴完整记录；不要在未验证前把实验性写法当成正式修复
