# 设置项：唯一值与那个老 BUG

设置项的值**不是随便写的**，游戏数据里每个键都有固定类型和合法值。**类型与可写值的权威表是 `data/setting-schemas.tsv`（268 个键）＋ `data/enum-values.tsv`（枚举原文）**；`data/settings.tsv` 只是它的子集，255 个键（370 行，另有 5 行键名为空），**缺 13 个键的类型与值**（`可用武器`、`职责限制`、`急救包刷新`、`游戏模式开始`、`英雄限制`、`英雄池上限`、`英雄选择`、`重装职责被动生命值加成`、`首先激活的控制点`、`有效控制点选择`、`旗手技能`、`锁定使用过的英雄`、`难度`）。

**「设置键一共多少个」按这个口径答（2026-10-24 逐表核过）：**

- **设置键（权威）= 282**：`setting-schemas.tsv` 268（125 个 schema 里 474 条有键名的条目去重）＋ 大厅 12 ＋ 主程序 2（`描述` / `模式名称`）。复现：`python tools/ws.py 知道 --audit`，打印「设置键 282 个」。
- **能敲进 .ow 的具体键名 = 753**：上面的 282 按 `%1$s` 模板展开成每个英雄的具体键名（`幽灵形态冷却时间` 这类）＋ 英雄官方键，即 `data/setting-keys.tsv` 的 757 减 4 个 `%1$s` 模板。复现：`tail -n +2 data/setting-keys.tsv | cut -f1 | sort -u | wc -l`（757）。
- **游戏界面逐条列出的项 = 2969 条**：`data/settings-page-entries.tsv` 行数，等于 `data/settings-pages.tsv` 的 `entry_count` 合计。去重后 694 个具体名字（另有 5 个 `%1$s` 模板名），把大厅的 `玩家上限 队伍1` / `队伍2` 补上共 696。复现：`tail -n +2 data/settings-page-entries.tsv | wc -l`。
- **`settings.tsv` 单表 = 255**：唯一非空键。复现：`tail -n +2 data/settings.tsv | cut -f2 | grep -v '^$' | sort -u | wc -l`。

旧文档里的 **269** **对不上任何一张表**：`docs/INDEX.md` 把它写成「`settings.tsv` = 269 设置键」，但 `data/settings.tsv` 从 2026-10-20 落盘那天起就是 255 个唯一键（370 行 / 5 行空键），当时仓库里也还没有 `setting-schemas.tsv` / `lobby-keys.tsv` / `verified-keys.tsv` 这三张表可凑数。今天用「255 + 12 大厅 + 2 主程序」恰好也能算出 269，但那是巧合，不是当年的算法——**269 来源不可考，别再引用**。

## 一、三类键，三套写法

| 类型 | 怎么写 | 例 |
|---|---|---|
| **BOOL** | 只能写 `开启` / `关闭` | `允许切换英雄: 关闭` |
| **ENUM** | 照抄枚举原文（表里的 allowed） | `重装职责被动生命值加成: 禁用`、`英雄限制: 关闭` |
| **FLOAT / INT** | 数字或百分比 | `复生时间: 1%` |

## 二、那个老 BUG 的真相

工坊把设置项导出成文本时，**布尔项写的是数据里的显示词（`启用` / `禁用`），但导入器只认 `开启` / `关闭`**。所以复制出来的脚本原样贴回去会报错，手改成 `关闭` 就能导入（实测）。

数据能证明这不是我们理解错：474 条有键名的设置项（原始导出 547 条目，其中 73 条没有键名）里，**145 条布尔项没有任何一条把“假”写成 `关闭`**（106 条 `禁用`、36 条空、2 条 `否`、1 条 `启用`）；但 `关闭` 能进、`禁用` 不能进——说明导入器用的是另一套规范词。

**所以拿到导出文件先跑这个，别手改几十行**：

```bash
python tools/ws.py fix 文件.ow --fix-bools
```

校验器认得出这种文件：同一份里这类问题 ≥8 条时会合成一条提示，直接指向上面的命令（E-24）。

## 三之二、值校验靠哪几张表（2026-10-24 接线后）

| 表 | 管什么 | 谁生成 | 生效范围 |
|---|---|---|---|
| `data/setting-schemas.tsv` | 键的类型 / 归属 schema / 每个 schema 的 Min~Max / 编辑器显示词 | `tools/gen_setting_schemas.py`（源：CASC `ruleset_schemas.json`） | 类型判定、层级判定、`settings` 生成回填 |
| `data/setting-ranges.tsv` | 数值键的上下界（454 键，含英雄技能层） | 手工维护（游戏数据 + 实机滑杆） | `check_setting_range`，error 级 |
| `data/setting-ranges-lobby.tsv` | 大厅滑杆边界（界面里才看得到） | 手工维护（实机） | 同上，warning 级 |
| `data/setting-values.tsv` | **词类键的合法取值**（13 个 ENUM 键，多 schema 取并集） | `tools/gen_setting_values.py`（源：`setting-schemas.tsv` + `enum-values.tsv`，`--check` 防漂移） | `check_setting_enum_values`，error 级 |
| `data/setting-aliases.tsv` | 导出显示词 → 导入词的改写表（`禁用→关闭`…），以及「这个词在这个键上合法」的例外（`重装职责被动生命值加成: 禁用`） | 手工维护（每条带实测证据） | `check_setting_bools` / `ws.py fix --fix-bools` 的词表来源 |

三条口径，写代码时别再踩：

1. **数值走范围、词类走词表**。`setting-ranges.tsv` 只放数字，别往里塞词；`setting-values.tsv` 只放词，别往里塞范围。
2. **多 schema 一律取并集**。同一键在不同模式页的选项集常常不同（`可用武器` 7 项来自 3 个 schema；`获胜得分` 6 段范围来自 18 个 schema）。
   并集只会少报（跨模式放行），不会误报；按单个 schema 收紧需要块上下文，而 lint 是按行扫的。
3. **百分比要换算**。编辑器与导出把 FLOAT 写成 `150%`，范围表存的是倍数（1.5）。
   `check_setting_range` 会先除 100 再比 —— 不换算的话这类行**根本不进检查**（9 份语料 945 处，全都没被查过）。

改这三张表之后必须跑：`python tools/ws.py check-all`（正 82 / 反 55）、
`WS_CORPUS=<私有仓>/corpus/real python tools/ws.py corpus`（9 份真实语料无新增 error）、
`python tools/gen_setting_values.py --check`（无漂移）。

## 三、为什么 `重装职责被动生命值加成: 禁用` 又能过

因为它**不是布尔项，是枚举**，`禁用` 是它的三个合法选项之一（`始终启用` / `1重装，2输出，2支援` / `禁用`）。

所以规则不能简化为“见到禁用就改成关闭”——只有 BOOL 项才那样，ENUM 项照抄原文。

## 四、报错长什么样

布尔项写错时，游戏报的不是“值非法”，而是指向块开头：

```
错误：第 N 行的"综合 {"之后应有一个游戏模式设置
```

定位方法：看那个块里第一个键值对，往往就是它。

## 五、表怎么来的（可复现）

游戏数据里有完整的设置项定义（`STUGameRulesetSchema`：每条带类型、布尔真/假词、枚举选项）。OWLib 自带的 `list-game-ruleset-schemas` 崩了，所以我们在 `workshop-data-update` 技能里加了自己的导出命令 `list-settings-words`，输出再压成 `data/settings.tsv`。数据更新后重跑即可。

### 大厅分区：12 个键已定位，下面 8 个有实测样本

```
大厅
{
	数据中心设置: 最佳设置
	最低延迟（毫秒）: 100000000
	比赛语音聊天: 启用
	玩家上限 队伍1: 4
	玩家上限 队伍2: 4
	玩家断线时暂停游戏: 是
	自由混战人数上限: 10
	队伍平衡: 攻防轮换后
}
```

- `最低延迟（毫秒）` 用的是**全角括号**，不能写成半角
- `自由混战人数上限` 只在**死斗类模式开启时**才出现（团队模式下不写）
- `队伍平衡` 可写 `关闭` / `攻防轮换后` 等
- 死斗这类无可调项的模式，在 `模式` 里是**单行无花括号**条目（`死斗` 独占一行），与赏金猎手同形

### 数据中心设置

- **默认 `最佳设置` 时，导出脚本里不会出现这一项**——模板里不要写
- 只有手动指定区域才会写出来，可选值仅 4 个：`中国北京` / `中国成都` / `中国杭州` / `中国深圳`
- 它不在工坊数据里（`workshop_zhCN.json` 搜不到），只能靠界面确认

## 默认值怎么体现（按分区不同，不是一条铁律）

工坊导出设置时**按分区处理**，不能一概而论：

| 分区 | 保持默认时 |
|---|---|
| 大厅 / 比赛类数值项（数据中心、语音聊天、断线暂停、队列加入、最低延迟…） | **不出现** |
| 模式、地图、英雄列表等结构项 | **照常列出**（即使没改） |

所以：

1. 别把"没出现"当成"这个键不能用"——它可能只是默认值
2. 也别把"出现"当成"改过"——结构项会无条件列出
3. 写模板时，数值项只写要改的；结构项按真实样本照抄
4. 判断依据优先看**真实样本**，其次看界面默认值

## 层级从哪来（2026-10 实测结论）

把设置项的原始 STU 记录逐字段解出来后确认：**数据里没有父级/分组/页面字段**，界面层级是客户端界面 + `.ow` 语法硬编码的。

- `m_category`（Modes/Combat/WeaponAmmo/HeroSpecific/HeroCommon）**不划层级**：同一 schema 内取值一致，跨 schema 又重复，是遗留标签
- `m_37D4F9CD`（0~16，有负值）取值不单调，**不能当排序/分页**
- 全量类型名表检索 `MENU|_PAGE|OPTION|FRONTEND|LAYOUT` → **0 命中**，没有任何界面布局资源

**但层级可以从"引用关系"推出来**，共三处：

| 引用 | 含义 | 数据文件 |
|---|---|---|
| `STUGameMode.m_gameRulesetSchemas[]` | 模式 → schema 列表 | `data/mode-schemas.tsv` |
| `STUHero.m_gameRulesetSchemas[]` | 英雄 → schema 列表 | `data/hero-schemas.tsv` |
| `STUGameRulesetSchemaEntry.m_3E783677` | 键 ID（ruleset 取值外键） | `data/schema-keys.tsv` |

### 一个反直觉但重要的事实

**块归属是自由的。** `重装职责被动生命值加成` 在 `deathmatch.ow` 写在 `综合`、在 `team.ow` 写在 `死斗`，**两份都能导入**。

导入器是按"该模式的全部 schema 并集"解析键名的，不按块名。所以真正要保证的不是"键写在哪一块"，而是 **"这个键属于该模式/英雄的 schema 并集"**。

### 由此得到的硬规则

1. `模式 > 死斗` 一类块的可用键 = 该模式 schema 列表里所有键的并集
2. `英雄 > 死神` 一类块同理，用英雄的 schema 并集
3. `大厅` 的键（`地图轮换` / `观战者人数上限` / `返回大厅` / `最低延迟（毫秒）`…）**在 125 个 schema（474 条有键名条目）里一个都查不到** → 只能硬编码词表（12 个键见 `data/lobby-keys.tsv`；`data/settings-blocks/hall.ow` 只写了其中 7 个）
4. 块内的键顺序在数据里无承载，导入无所谓，**不要声称与官方样本逐行一致**

### 纠正一个旧数字

`ruleset_schemas.json` 实际是 **125 schema / 547 条目**（曾按 374 记录，那是旧版导出的口径）。其中**只有 474 条带键名**（另 73 条无名），去重后 **268 个键名** —— `data/setting-schemas.tsv` 就是这 474 行，`data/settings.tsv` 从这条路只拿到 255 个（少 13 个）。

## 大厅那 12 个键：出处已找到

数据不在 ruleset schema 里（474 条有键名条目、547 条全量，0 命中），但在另一个资源里：

- 资产 **`000000000003.10F`**（类型 `0x10F`，全库唯一，20.6 MB）
- 资产内**连续一段**（第 1415–1440 条文本引用）引用了大厅全部 12 个键，数量精确闭合
- 定位手法：按 STU 字符串引用的位模式扫（`0x7C` 类型经 bit-flip 后 GUID 第 6–7 字节恒为 `E0 0D`），扫 15.2 万个资产后唯一命中

**已确认**
- `玩家上限 队伍1` / `玩家上限 队伍2` 在数据里是**同一个键的两个实例**（`玩家上限 %1$s` 被引用两次），不是两个独立键
- 集合完整：正好 12 个，不多不少

**未确认（两条，别当结论用）**
1. `0x10F` 里的记录顺序与 `.ow` 的书写顺序**近乎相反**，反向读也不等同样本 → 生成 `.ow` 仍用实测样本顺序（现 `data/lobby-keys.tsv` 就是这么排的）
2. **值**（观战者=6、最低延迟=100000000、队伍平衡=攻防轮换后）在数据里没有静态出处——`0x10F` 只引用标签、不引用枚举，值属房间运行时状态 → 继续用实测样本的默认值

**顺带排除的两条路**
- 本地存档 / 预设：`Documents/Overwatch/Settings/Settings_v0.ini` 只有渲染与音频 47 行，`_retail_/CC/db` 三个 LevelDB 是 175 字节空桩 → 房间参数不落本地
- 语言表：`0x07C` 6.4 万条文本里 12 键全部命中并拿到字符串 ID；`0x2C40–0x2C64` 有一整簇 OW1 大厅文案，可能还藏着第 13 个键（`平衡调整时间点`、`地图顺序`），但 `0x10F` 未引用 → 未确认

## 大厅栏位的数值边界（2026-10-23 实机确认）

大厅那 12 个键里，只有 4 个是「数值 + 界面滑杆」的，边界如下（滑杆拉到最右就是上限）：

| 键 | 下限 | 上限 | 备注 |
|---|---|---|---|
| 玩家上限 队伍1 | 0 | 12 | 写 0 = 这一队没人 |
| 玩家上限 队伍2 | 0 | 12 | 同上 |
| 观战者人数上限 | 0 | 12 | 单独一套栏位，不占玩家位（下限可到 0，2026-10-23） |
| 自由混战人数上限 | 未确认 | 12 | 死斗 / 自由混战类用 |

**两队要加起来看**：队伍1 + 队伍2 合计最多 **12** 人——`6+6`、`8+4`、`12+0` 都行，`7+6` 不行（两个键单看都没超，加起来才露陷）。
**最少 1 人**：`0+0` 开不了局，但 `12+0` 这种「只开一队」是合法的。
**默认各 5 人**：新建房间时两队都是 5（合计 10）。所以**只写一队时，单队最多写到 7**（7+5=12）；写 8 就已撞线，哪怕另一队你根本没提。

校验器怎么处理（`data/setting-ranges-lobby.tsv` + `check_lobby_team_sum`）：

| 情况 | 报什么 | 级别 |
|---|---|---|
| 单键写 13 以上 | `玩家上限 队伍1 的值 13 超出范围（0~12）` | **必改** |
| 两队合计超 12 | `玩家上限 队伍1 + 队伍2 合计 13 人，超过大厅总共 12 个栏位` | **必改** |
| 只写了一队且超过 7 | `另一队没写、按大厅默认 5 人算，合计 13 超过 12 个栏位` | **必改** |
| 团队模式写了自由混战人数 | `团队模式下 自由混战人数上限 必须写 0` | **必改** |
| 死斗模式把自由混战写成 0 | `死斗类模式里 自由混战人数上限 至少 1` | **必改** |
| 两队都是 0 | `合计 0 人，大厅至少要留 1 个栏位才能开局` | 提示（导入多半没事，只是开不了局） |

**`自由混战人数上限` 跟模式挂钩**（2026-10-23 实机）：团队模式（占领要点 / 攻击护送 / 攻防 / 推进 / 运载 / 闪点 / 决斗先锋 / 勇夺锦旗 / 团队死斗）必须写 **0**；死斗类（死斗、赏金猎手）**至少 1**。认不出的模式、两种模式混写时不判。

为什么敢报「必改」（2026-10-23 实机）：游戏界面里根本输不进超过 12 的数（会自己弹回 12），但**外部写进 `.ow` 再复制进去，导入会报错**。所以越界值是必然失败，不是风格问题。

游戏侧两种提示，看到哪个都是同一类问题：

| 场景 | 游戏显示 |
|---|---|
| 界面里改完想返回上一级 | 弹窗「大厅设置无效。你必须调整或撤销改动。」 |
| 外部导入 `.ow` | 右上角「错误：无效的队伍设置」（`errors.tsv` 65729，`ws.py explain 队伍` 可查到原文） |
（边界本身仍来自界面观察，不在游戏数据里：`0x10F` 只引用标签、不引用值。）

**跟扩展点数的关系**：栏位腾得越少，可用扩展点数越多（`可用点数 = 4 × 空栏位数`，见 `docs/extensions.md` 第七节）。校验器**不**按栏位反推点数：大厅键在真实文件里常被整段省略，输入不可靠。
