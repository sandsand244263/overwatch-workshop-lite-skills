# 硬上限（元素数 / 规则 / 变量 / 子程序）

工坊有几处写死的容量限制，超了不是"性能差"，是**保存或导入直接失败**。这张表是唯一入口。

## 一、上限一览

| 项 | 上限 | 细节 | 可信度 |
|---|---|---|---|
| **元素数** | 32768 | 整个模式所有元素之和（动作参数、条件、值函数都算） | 既有记载，未在 2.25.0.0 实测 |
| **单条规则大小** | 98 KB | 一条规则的文本容量，长规则先撞这个 | 既有记载，未实测 |
| **全局变量** | 128 个 | 索引 0–127，可跳号 | `syntax.md` + VS Code 插件语法 |
| **玩家变量** | 128 个 | 同上，与全局变量分开计数 | 同上 |
| **子程序** | 128 个 | 索引 0–127，可跳号 | 同上 |
| **大厅玩家栏位** | 12 | `玩家上限 队伍1 + 队伍2` **合计** ≤ 12；单队滑杆最右也是 12；合计 0 开不了局；界面里输不进 >12，外部写进去**导入会报错** | 2026-10-23 实机确认 |
| **观战者 / 自由混战人数上限** | 各 12 | 界面滑杆最右；观战不占玩家栏位 | 2026-10-23 实机确认 |
| **规则条数** | 未确认 | 社区常传 100，没有确证，**不写死** | 待验证 |

## 二、为什么工具提取不到

这些数字是**客户端代码里的常量**，不在可读数据里：

- STU 类型里搜不到 `Limit` / `Max` 相关的设置项字段
- DataTool 也没有对应命令（`list-workshop` 只给元素与枚举，不含容量）

所以别指望自动导出，只能靠文档 + 实测。

## 三、现在能自动检查的部分

`tools/ws.py check` 已经覆盖：

- 变量索引 > 127 → 报错
- 全局变量 / 玩家变量各超过 128 个 → 报错
- 子程序索引 > 127、数量超过 128 → 报错

**元素数和规则大小没法静态精确算**，但元素数可以在游戏里直接读：

> 地图工坊 → 显示诊断结果 → 总计元素数量

插件混淆功能也是让你先填这个数（它的校验就用 32768）。所以流程是：导入后在工坊里看诊断，超了就按 `cost-patterns.md` 降级。

## 四、元素数怎么估

已标定（2026-10-20，25 个探针实测，`ws.py count` 与实测 **18/18 完全一致**）。

### 公式

| 节点 | 成本 |
|---|---|
| 规则 | 1 |
| 动作 | 1 |
| 条件 | 1 |
| 顶层参数 | 成本减 1（最低 0） |
| 数字（含 0、小数） | 2 |
| 变量访问 `全局.X` / `事件玩家.X` | 2 |
| 裸常量 | 标量（白色/球体/可见…）恒为 1；**集合类（所有队伍/所有玩家…）嵌在函数里时 2** |
| 值函数 | 1 + 各参数 |
| `数组(...)` | 2 + 各项 |
| `自定义字符串(...)` | 5 + 每个插值 `{n}` |
| 子程序声明 | 0 |
| 设置块 / 变量块 / 事件块 / 注释 | 0 |

### 验证

25 个探针（`tools/probes/calib/`，实测数字在 `measurements.csv`）覆盖：规则骨架、动作数量、数字大小、条件数量、嵌套值、数组 1/3 项、字符串 0/1 插值、子程序调用、变量作目标/值/进数组、变量名、嵌套常量。模型全部命中。

### 边界

- 英雄字面量成对出现、HUD/特效类动作的额外开销**未覆盖**，这类地方仍可能有偏差
- 估算用于写之前别撞 32768；最终数字以游戏「显示诊断结果 → 总计元素数量」为准
- 官方改算法时重跑这 25 个探针即可重新标定

## 五、写代码时的默认纪律

- 变量别开满 128，留余量（改版加变量时不用重构索引）
- 长规则拆成多条，避免撞 98 KB
- 装饰类常驻特效默认按"最小可见"给（本地玩家可见 / 近距离可见），别默认全房

## 元素估算（合并自旧 element-audit）

估算器在 `tools/element_count.py`，25 个探针实测标定，**25/25 命中**。

| 项 | 成本 |
|---|---|
| 规则 / 动作 / 条件 / 值函数 | 1 |
| `数组` | 2 |
| 字符串 | 5 + 插值数 |
| 数字 | 2（`数值()` + 字面量） |
| `全局.A` 一类访问 | 2 |
| 裸常量（标量） | 1；集合类（`所有队伍`…）嵌在函数里 2 |
| `While` / `If` | 1 + 条件；条件含比较运算符固定 +3 |
| `End` / 子程序声明 | 0 |
| 动作与条件的**顶层参数** | 各减 1 |

**用法**：`python tools/ws.py count 文件.ow`。只做数量级预警，最终以游戏诊断为准。

**边界**：混淆后的代码误差大（实测 88→154，估算器给 72），混淆版只报原码与混淆码两个数字，不给差值。

**历史**：早期 76 条手工实测基准不统一、覆盖不到 15%，已废弃——正确做法是「同模板只改一处」的探针。

## 元素数：小文件精确，大文件系统性低估（2026-10-21 实测）

| 场景 | 我们的估算 | 游戏显示 | 结论 |
|---|---|---|---|
| 37 个小探针 | 精确命中 | — | 单条构造的成本是对的 |
| 235 KB 真实模式 | **7,668** | **16,918** | **低估 2.2 倍** |

小探针全中的原因是它们只含少数构造；真实模式的元素数被游戏按一套我们还没解出的规则累计（比较链、数组项、字符串插值、三元表达式都参与）。

**当前做法**：估算 ≥ 1500 时，`count` 额外输出按系数 **2.2** 校准的值（16,869 vs 实测 16,918，差 0.3%），并提示按校准值判断 32,768 上限。

**没做的事**：没有为了"看起来准"去微调系数——2.2 来自一个真实样本，样本量是 1。再多几个真实文件的官方计数（编辑器里能看到）就能拟合出可靠模型。

## 元素数：探针路线的结论（2026-10-21，13 个探针）

**游戏自己的定义**（诊断面板原文）：`元素包括规则、条件、行动和值（最多可有32768个）`

**已经测准的单价**（每个探针单独导入，全是 100 次重复）：

| 构造 | 单价 | 探针 |
|---|---|---|
| 动作语句 | 1（另加各参数的值节点） | E0 = 201 |
| 数字字面量（普通位置） | 1 | E0 |
| 数字字面量（数组内） | 2 | E1 = 1001 |
| 字符串字面量 | 3 | FB = 501 |
| 布尔 / 空 | 0 | FA = 101 |
| `自定义颜色(...)` | 4（+ 4 个数字） | FC = 901 |
| `数组(...)` | 1 + 每个元素随内容计 | E1/E3 |
| 条件行 | 1 + 其中数字 1 个 | E4 = 303 |
| 乘法表达式 | 数字 + 运算符 | S2 = 939 |

**没解出来的**：`If/While/For` 块会额外加价（K5=12 而节点模型给 5），且真实文件里块、值、数组嵌套组合后的加价规则无法从单价推出。

**两条路线都被证伪**：
- 「纯节点计数」→ 17/45 个标定失配（块结构全错）
- 「现用经验模型」→ 45 个标定全过，但真实文件低估 2.12 倍

**结论**：元素数在**小规模精确、真实规模系统性低估**。当前 `count` 对 ≥1500 的文件给出 ×2.12 的校准值并明确标注，仅供 32,768 上限预警。

**要 100% 精确只有一条路**：实测推导客户端的计数函数（诊断面板那个「总计元素数量」）。

## 元素计数：最终口径（2026-10-22，实测推导 + 19 个探针）

`ws.py count` 现在默认用**实测推导模型**（`tools/element_count2.py`），旧经验模型保留为 `count --legacy`。

**单价表（全部有探针依据）**

| 构造 | 单价 |
|---|---|
| 规则 / 语句（动作、条件各 1） | 1 |
| 数字字面量（普通位置） | 1 |
| 字符串字面量 | 3（每个 `{n}` 插值 +1） |
| 布尔 / 空 / 枚举词 | 0 |
| `自定义颜色(...)` | 4 |
| 数组 / 每个元素槽位 | 1 / 1（元素里的数字按 2） |
| `全局.X` 取值 | 1 |
| **`事件玩家.X` / `本地玩家.X` 取值** | **2**（G2=301） |
| **变量下标 `X[i]`** | 下标本身 **+2**（H1=501） |
| **三元 `条件 ? a : b`** | 本体 **5** + 三部分（G3=1101） |
| `自定义字符串` 插值参数 | 0（只算字符串本体） |
| If / While / Else If / For 块 | 5 / 5 / 5 / 5 |
| 子程序调用 | 1（H2=104） |
| 事件块、事件行 | 0（J2=3） |

**精度**

| 场景 | 误差 |
|---|---|
| 单元探针（E/G/H 系列，11 个） | **0** |
| 单条真实规则 R1（2175） | +3（0.1%） |
| 小样本标定 37 个 | 25 个精确，最大偏差 6，平均 1.9 |
| **原版 235 KB（16918）** | **-553（-3.3%）** |

**分片残差**：4 个分片 -215 / +98 / -422 / -14。剩余误差集中在**复杂表达式**（三角公式、多层括号与除法）较多的规则里，算术运算符并非统一单价；继续追需要再取样，已停。

**结论**：`count` 对 ≤2000 元素给「±6」，对更大文件给「-3%~-4%」；32,768 上限预警按校准值判断足够。

## 元素估算在真实模式上的精度（2026-10-23 实测 5 份）

| 模式 | 规则数 | 游戏实测 | 模型估算 | 偏差 | 真实/估算 |
|---|---|---|---|---|---|
| 猪猪钩钩乐·原版 | 165 | 16918 | 16226 | −4.1% | 1.043 |
| 下100层 | 198 | 31515 | 29781 | −5.5% | 1.058 |
| 丧尸守桥 | 149 | 6355 | 5642 | −11.2% | 1.126 |
| 搜打撤 | 49 | 9924 | 8054 | −18.8% | 1.232 |
| 暴打大锤3（fix 后） | 366 | 32738 | 28798 | −12.0% | 1.137 |

**结论：真实文件一律偏低，倍率 1.04~1.23，与文件规模无关、与任何单一特征都不相关。**

`ws.py totals` 直接打这张表（含倍率列），倍率区间就是 `count` 修正系数的来源。

已排除的原因（都做过对照实验）：

| 猜测 | 实验 | 结果 |
|---|---|---|
| 语法未解析、语句被漏算 | 数零成本语句 | 0 条 |
| 下标赋值太便宜 | Q3 探针（10 次） | 模型反而高估 1/条 |
| `地图工坊设置*` 调用 | Q1b 探针（10 次） | 只差 1/条 |
| 普通赋值 | Q2 探针（10 次） | **完全一致** |
| UI 调用（创建…） | 四个文件交叉比对 | 数量与偏差无相关性 |
| 某一类构造（字符串 / 三元 / 下标 / 事件玩家 / 事件行） | 5 份真实文件的残差/计数归因（2026-10-23） | 所有候选的跨文件离散度 ≥0.34，**没有单一构造能解释** |

### 现在的口径（2026-10-23 起）

`ws.py count` 按元素量分两档，**区间只向上给**（模型在真实文件上一律偏低，报大了顶多保守，报小了会让人撞上限）：

| 量级 | 输出 | 依据 |
|---|---|---|
| < 2000（探针级） | 精确值，偏差 ≤6 | 43 个标定探针 |
| ≥ 2000（真实模式） | `模型估 X，真实值多半在 ×1.03X ~ ×1.25X` | 5 份实测倍率 1.043~1.232，上界各留余量 |

上限 32768 的判定按**上界**判，分三种：

- 下界就超 32768 → `✗ 必定超上限`
- 上界超 32768 → `⚠ 可能超上限`（真实值落在上限两侧，只能进游戏核对）
- 都为安全 → 打「最坏情况还余 N 个」

**旧版错误**：v3.10.21 及以前输出 `×0.80 ~ ×1.06`，方向与实测相反（暗示可能比估算小，实际只会更大），已修。

要把这 4%~19% 彻底消掉，得按「参数个数 / 嵌套深度 / 表达式复杂度」做 10 个以上组合探针，
或在真实模式上做单点删减对照（删全部块 / 删全部三元 / 删全部 `事件玩家`，各测一次）。
成本高于收益，记录在此，等真有需求再动。
