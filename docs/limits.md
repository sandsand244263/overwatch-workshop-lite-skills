# 硬上限（元素数 / 规则 / 变量 / 子程序）

工坊有几处写死的容量限制，超了不是"性能差"，是**保存或导入直接失败**。这张表是唯一入口。

## 一、上限一览

| 项 | 上限 | 细节 | 可信度 |
|---|---|---|---|
| **元素数** | 32768 | 整个模式所有元素之和（动作参数、条件、值函数都算） | 既有记载，未在 2.25.0.0 实测 |
| **单条规则大小** | 98 KB | 一条规则的文本容量，长规则先撞这个 | 既有记载，未实测 |
| **全局变量** | 128 个 | 索引 0–127，可跳号 | `syntax.md` + VS Code 插件语法 |
| **玩家变量** | 128 个 | 同上，与全局变量分开计数 | 同上 |
| **子程序** | 128 个 | 索引 0–127，可跳号 | 同上 |
| **规则条数** | 未确认 | 社区常传 100，没有确证，**不写死** | 待验证 |

## 二、为什么工具提取不到

这些数字是**客户端代码里的常量**，不在可读数据里：

- STU 类型里搜不到 `Limit` / `Max` 相关的设置项字段
- DataTool 也没有对应命令（`list-workshop` 只给元素与枚举，不含容量）

所以别指望自动导出，只能靠文档 + 实测。

## 三、现在能自动检查的部分

`tools/ws.py check` 已经覆盖：

- 变量索引 > 127 → 报错
- 全局变量 / 玩家变量各超过 128 个 → 报错
- 子程序索引 > 127、数量超过 128 → 报错

**元素数和规则大小没法静态精确算**，但元素数可以在游戏里直接读：

> 地图工坊 → 显示诊断结果 → 总计元素数量

插件混淆功能也是让你先填这个数（它的校验就用 32768）。所以流程是：导入后在工坊里看诊断，超了就按 `element-audit.md` 降级。

## 四、元素数怎么估

已标定（2026-10-20，18 个探针实测，`ws.py count` 与实测 **18/18 完全一致**）。

### 公式

| 节点 | 成本 |
|---|---|
| 规则 | 1 |
| 动作 | 1 |
| 条件 | 1 |
| 顶层参数 | 成本减 1（最低 0） |
| 数字（含 0、小数） | 2 |
| 变量访问 `全局.X` / `事件玩家.X` | 2 |
| 裸常量（`真`/`空`/`无视条件`…） | 1；**嵌在值函数里时 2** |
| 值函数 | 1 + 各参数 |
| `数组(...)` | 2 + 各项 |
| `自定义字符串(...)` | 5 + 每个插值 `{n}` |
| 子程序声明 | 0 |
| 设置块 / 变量块 / 事件块 / 注释 | 0 |

### 验证

18 个探针（`tools/probes/calib/`，实测数字在 `measurements.csv`）覆盖：规则骨架、动作数量、数字大小、条件数量、嵌套值、数组 1/3 项、字符串 0/1 插值、子程序调用、变量作目标/值/进数组、变量名、嵌套常量。模型全部命中。

### 边界

- 英雄字面量成对出现、HUD/特效类动作的额外开销**未覆盖**，这类地方仍可能有偏差
- 估算用于写之前别撞 32768；最终数字以游戏「显示诊断结果 → 总计元素数量」为准
- 官方改算法时重跑这 18 个探针即可重新标定

## 五、写代码时的默认纪律

- 变量别开满 128，留余量（改版加变量时不用重构索引）
- 长规则拆成多条，避免撞 98 KB
- 装饰类常驻特效默认按"最小可见"给（本地玩家可见 / 近距离可见），别默认全房
