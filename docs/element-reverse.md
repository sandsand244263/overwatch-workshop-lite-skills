> 目标：复刻客户端诊断面板里那个 `总计元素数量`（上限 32768）。
> 状态：**未完全成功**。13 个探针里 9 个精确命中，4 个差 ±1~2；235 KB 真实模式仍低估 14%。
> 本文只写实测过的东西，没验证的一律标注为「未验证」。

复跑命令：


## 一、结论摘要

| 项 | 结果 |
|---|---|
| 算法来源 | **不是**从二进制里读出来的，是从 13 个实测探针反推的单价模型 |
| 小探针（单构造） | E0/E1/E3/E4/E5/FA/FB/FC **8 个全中** |
| 组合探针 | R1B **全中**；S1 差 -2、S2 差 -1、R1A 差 -1、R1 差 +1 |
| 真实模式 235 KB | 预测 14533，游戏 16918，**低估 2385（-14.1%）** |
| 二进制定位 | **失败**，原因见第三节 |

结论：单个构造的单价已经测准，**多个构造叠在一起时还缺一条加价规则**，且这条规则在真实规模下累计 14%。

## 二、二进制搜索结果（失败，但过程可复跑）

游戏：`E:\Overwatch\_retail_\Overwatch.exe`，81 MB，静态只读，未启动进程、未注入、未挂调试器。

### 1. 段的布局

| 段 | VA | 原始大小 |
|---|---|---|
| `.text` | 0x1000 | 0x3508000 (55.6 MB) |
| `.rdata` | 0x3509000 | 0x1555e00 |

VA 换算：`VA = file_off - PointerToRawData + VirtualAddress`（`.text` 即 `VA = off + 0xC00`）。

### 2. 常量扫描（`tools/re/element_scan.py`）

诊断面板原文给出三个可交叉验证的常量：元素上限 32768、单条规则 98 KB、皮肤组合 12。

```
0x8000   32768 元素上限        .text 原始字节 667 处 -> 其中真作为指令立即数 451 处
0x18800  100352 = 98KB         20 处 -> 真立即数 6 处
0x18000  98304 = 96KB          131 处 -> 真立即数 3 处
0x7fff   32767 = 上限-1        358 处 -> 真立即数 280 处
```

「真立即数」= 把命中点当作地址回填进反汇编，确认它落在某条指令的 imm 位（排除跳转位移、
浮点常量、跳转表数据造成的假阳性）。451 个 32768 立即数里没有任何一个和 98 KB 的 6 个命中点
相距 0x800 字节以内，**交叉定位没有产出唯一候选**。

### 2.1 按函数归类（`.pdata` 异常表，比固定窗口准）

`.pdata` 从 VA 0x5725000 起、0x24e600 字节，每 12 字节一条 `RUNTIME_FUNCTION`
（BeginAddress / EndAddress / UnwindInfoAddress），共解出 **201481 个函数**。用它对命中点做归属：

```
含 32768 立即数的函数            325 个
其中同时含 32767(0x7FFF) 的      30 个   <- 都是 min(x, 32768) 这种 clamp 惯用法，不是诊断
同时含 98KB(0x18800/0x18000) 的   0 个
```

**这是本轮最硬的一条否定结论**：51 万条指令范围里，没有任何一个函数同时检查「元素上限 32768」
和「单条规则 98 KB」。要么元素数上限在代码里不是 0x8000（可能是 `> 0x7FFF` 判定或别的编码），
要么元素计数本来就和规则长度校验不在一个模块里。

### 2.2 按函数归类这一步可复用

`section('.pdata')` 解析 RUNTIME_FUNCTION 表 + `bisect` 定位归属，是这套工具里最有价值的一步：
它把「函数边界」做准了，后面任何常量/字符串的引用都能按函数聚合，不需要 IDA 的交叉引用。
已写进 `tools/re/element_scan.py` 的 `functions()` / `owner()`（见脚本）。

### 3. 唯二值得记下的两个候选点

98 KB 的 6 个真命中里，有两个看起来像「规则文本长度上限」：

**(a) 0x942250 — 疑似上限 getter**

```
0x942250  b8 00 88 01 00        mov     eax, 0x18800        ; 100352
0x942255  c3                    ret
```

前面 0x942240 是一个 `mov eax, [rip+...]; ret` 的同类 getter，说明这一片是「常量 getter 函数群」。
它只返回 100352，没有配对的 32768。

**(b) 0x3346018 — 疑似「规则太长」判定**

```
0x3345ff8  lea     ecx, [rip + 0x21868ea]
0x3345ffe  call    0x21d77e0                ; 取串/格式化
0x334600e  call    0x21d7840
0x3346013  test    dil, dil
0x3346016  je      0x3346032
0x3346018  cmp     qword ptr [r14], 0x18800 ; 长度 >= 100352 ?
0x334601f  jge     0x3346032                ; 超了就跳到失败分支
0x3346021  lea     rcx, [rsp + 0x20]
0x3346026  mov     bl, 1
0x3346028  call    0x298be00
```

结构是「先拼提示串、再比长度、超了走另一支」，形状像尺寸校验 + 报错，但它所在函数前后
0x4000 字节内**没有任何 32768 立即数**，所以它不是那个同时判「元素数」和「规则长度」的诊断函数。
它更像是编辑器侧的「这条规则文本太长」门禁。

### 4. 为什么这条路走不通

- **字符串不在 exe 里**。`.rdata` 里搜 `Element/Workshop/元素/自定义颜色/数组` 的 UTF-16 与
  ASCII 形态，全部 0 命中（只有 `element` 3 处、`limit` 28 处这种无关通用词）。客户端的工坊
  名字表在 CASC 的语言包里，exe 里只有 ID，所以「先找串、再找引用、再读表」这条路直接断。
- **常量噪声太大**。32768 是 2 的 15 次方，在 55 MB 代码里被大量 memcpy/分配/位图逻辑复用，
  451 个立即数里手工筛不可能收敛。
- **没有调试器/IDA**。没有交叉引用（xref）就只能靠「常量邻近 + 循环形状」猜函数边界，
  在 55 MB 里命中率极低。

如果后面要接着做，见第七节的线索。

## 三、从探针反推出的算法（这部分是实测的）

### 3.1 伪代码

```
count(program):
    total = 1 * 规则数                                    # 每条 规则(...) 记 1

    for 每条规则:
        for 每条条件语句 cond:  total += stmt_cost(cond)
        for 每条动作语句 act:   total += stmt_cost(act)

stmt_cost(语句):
    if 语句是 End:                       return 0
    if 语句是 块头(If/Else If/Else/While/For):
        base = {If:5, Else If:5, Else:3, While:5, For:5}
        return base + Σ cost(条件里的每个值)
    if 语句是 赋值 (目标 = 值):
        v = 1                                            # 语句本身
        if 目标带下标 [..]:  v += 1 + Σ cost(下标表达式)   # 槽位 + 下标里的值
        return v + cost(值)
    if 语句是 条件行 (A == B / A && B ...):
        return 1 + cost(A) + cost(B)                     # 比较符本身不计
    if 语句是 动作 (名(参数...)):
        v = 1
        for i, 参数 in enumerate(参数):
            if i == 0 and 动作 in 写操作:  continue        # 写目标不计
            v += cost(参数)
        return v

cost(值节点):
    数字字面量                 -> 1
    字符串字面量               -> 3 + 插值数({n} 的个数)
    变量取值 全局.X / 事件玩家.Y -> 1 (+ 下标表达式)
    集合常量(所有队伍/事件玩家/主机玩家/双方/攻击方...) -> 1
    枚举/布尔/空/效果名(白色/真/空/顶部/球体/有益爆炸...) -> 0
    值函数 名(参数...)         -> 本体 + Σ cost(参数)
        本体默认 1，但 自定义颜色 = 4
        自定义字符串: 本体 1 + 字符串本体 3 + 插值数，**插值参数不再单独计**
    数组(a,b,c)                -> 1 + Σ(1 + cost(项))   # 每项先占 1 个槽位
    二元运算 a op b            -> 1 + cost(a) + cost(b)（在数组项里 op 记 2）
    一元 !x / -x               -> 1 + cost(x)
    三元 条件 ? a : b          -> 1 + cost(条件) + cost(a) + cost(b)   # 未验证
```

### 3.2 单价与实测依据

| 构造 | 单价 | 依据（探针 = 单独导入游戏 100 次重复后反推） |
|---|---|---|
| 规则 | 1 | E0 = 201 = 1 + 100×2 |
| 动作语句 | 1 | FA = 101 = 1 + 100×1（参数是布尔，记 0） |
| 条件语句 | 1 | C05 = 4 = 1 + 1 + 2（真==真 记 1 + 等待 记 2） |
| 数字（普通位置） | 1 | E0 = 201 = 1 + 100×(1+1) |
| 数字（数组项） | 1+1=2 | E1 = 1001 = 1 + 100×(1 + 1 + 4×2) |
| 字符串本体 | 3 | FB = 501 = 1 + 100×(1 + 1 + 3) |
| 每个 `{n}` 插值 | 1 | C11 = 7 vs C10 = 6 |
| `自定义字符串` 的插值参数 | 0 | C11 = 7（若参数也计就变 8） |
| `自定义颜色(1,2,3,4)` | 4 + 4×1 = 8 | FC = 901 = 1 + 100×(1 + 8) |
| `颜色(白色)` | 1 | E5 反推；白色是枚举记 0 |
| `数组(...)` | 1 + 每项(1+内容) | E1/E3/C08/C09 |
| 变量取值 | 1 | D02 = 3 = 1 + 1 + 1 |
| 集合常量（所有队伍/主机玩家） | 1 | E01 = 4 = 1+1+2（所有玩家+所有队伍） |
| 枚举/布尔/空 | 0 | FA=101（真）、E5=1101（空/顶部/可见和字符串） |
| 赋值目标（无下标） | 0 | E0（设置全局变量(g,1) 记 2） |
| 赋值目标（带下标） | 1 + 下标值 | R1A = 93 |
| 二元运算符 | 1（数组项里 2） | S2 = 939（180 个 `(10000000*0.0000081)`） |
| `If(1 == 1)` 块 | 5 + 2 = 7 | K5 = 12 = 1 + 2 + 7 + 2 |
| `Else If(1 == 2)` 块 | 5 + 2 = 7 | K12 = 20 = 1+2+7+2+?+2 |
| `For 全局变量(i,1,5,1)` | 5 | K11 = 10 = 1 + 2 + 5 + 2 |
| `中断` | 1 | K9 = 13 = 1+2+7+2+1 |

### 3.3 解析器必须处理的三个坑

1. **块头可以跨行**：`While(` 换行、条件写在下面几行，`);` 结尾。按行切语句会把整条条件丢掉
   （实测真实模式里因此少算 357 条语句、少 2000+ 元素）。
2. **字符串可以跨行**，且字符串里的 `//` 不是注释。注释剥离必须先过字符串状态机。
3. **三元的写法是 `条件 ? 值1 : 值2`**，而且在真实模式里跨行写（`? 选择英雄的玩家(...) : 0,`），
   共 51 处。旧解析器把 `?` 当常量，整条参数解析崩掉。

这三条都已修在 `tools/element_count2.py`（`scan_units` 字符级扫描 + `P.parse` 的三元层）。

## 五、没解出来的点（卡在哪）

### 卡点 1：剩余 ±1~2 的误差没法用「再加一条单价」解释

四个偏差样本互相矛盾：

- S1（1 规则 + 1 条件 + 1 个大数组赋值）= 240，模型 238，差 **-2**。
- S2（同结构，数组换成 180 个乘法项）= 939，模型 938，差 **-1**。
- R1A（1 规则 + 1 条件 + 18 条动作）= 93，模型 92，差 **-1**。
- R1B（1 规则 + 1 条件 + 18 条动作，其中 16 个大数组）= 2088，模型 **精确**。
- R1（= R1B 的数组 + R1A 的 18 条动作）= 2175，模型 2176，差 **+1**。

把「R1 = R1B + R1A 那 18 条动作」当成减法题：12088 → 实测增量 **87**，而 R1A 单独测出来这
18 条动作值 **89**。同一段文本在两个文件里单价不同（差 2），说明我漏掉的东西**不是某个构造的
固定单价**，而是**块/语句的组合方式**上有条件加成（大概是「同一个值被复用」「同一规则里第 N 条
之后的语句」这类上下文相关规则）。三种假设都试过并被数据否掉：

| 假设 | 结果 |
|---|---|
| 加 1 条「条件行多算 1」 | C05 = 4 会变 5，立刻错 |
| 加 1 条「数组本体算 2」 | C08 = 5 会变 6，且 S2 变 940 |
| 加 1 条「插值参数也计」 | C11 = 7 会变 8 |

### 卡点 2：真实模式 -14% 的缺口定位不到

已知缺口 2385。逐项排查过、**每条都能被某个探针否掉**：

| 候选解释 | 真实增益 | 为什么否掉 |
|---|---|---|
| 事件语句也算元素（371 条事件） | +206 | 等价于把「规则」挪到「事件」，探针分不出，但只补 9% |
| 变量声明算元素（118 个全局/玩家变量） | +118 | **已排除**：R1B（118 个变量）精确命中，E0（1 个变量）也精确命中，若变量计元素两者不可能同时对 |
| 子程序声明算元素（38 个） | +38 | **已排除**：同上，R1B/S1/S2/R1A/R1 都带同一套 38 个子程序声明，残差却不相同（-2/-1/-1/0/+1） |
| 数字一律按 2 算（1268 个值位置数字） | +1268 | E5 = 1101 会变 1201 |
| 数组项槽位从 1 提到 2 | +756 | E1 = 1001 会变 1401 |
| 块结构加价（320 个块） | ≤ +640 | R1B/S1/S2 无块，无法用探针约束；但全加到块上也不够 |
| `事件玩家` 按 2 算（577 次） | +577 | 13 个探针里没有 `事件玩家`，**无法证伪**，是当前最可疑的一条 |

一个顺带得到的排除法：S1/S2/R1A/R1B/R1 这 5 个文件带着**同一套** 变量块（47 全局 + 71 玩家）
和 **38 个**子程序声明，残差却各不相同（-2 / -1 / -1 / 0 / +1）。所以「变量 / 子程序声明计元素」
这条被直接排除——否则它们的残差应该整体平移一个相同常数。

单条都不够，组合起来又互相冲突（总得有一条能被探针否掉）。这就是卡住的真实原因：**13 个探针
的构造覆盖不到真实文件里的组合形态**，缺的是「真实规模 + 单点改动」的对照组。

### 卡点 3：98 KB 与 32768 不在同一个函数

按诊断面板原文，两个上限应该在同一个诊断函数里被检查。实测 6 个 100352 真立即数、3 个 98304
真立即数，没有一个与 451 个 32768 立即数相邻（0x800 窗口）。要么元素数上限不是 0x8000 而是别
的编码（例如 `0x8000 - 1`、`cmp eax, 7FFFH` 后再 `jae`），要么元素计数和规则长度校验本来就在
两个模块里。0x7FFF 有 280 个真立即数，也做过同样的邻近检查，同样没有收敛。

## 六、这套模型现在能干什么

- 单规则、少构造的文件（探针级、小型模式）：基本精确，可以当「别撞 32768」的预警。
- 大型真实模式：**系统性低估约 14%**。要么按 ×1.16 粗校（16918 / 14533 = 1.164），要么别用它
  判断是否接近上限。注意这是用 1 个样本算出来的系数，样本量 1，不要当结论。

## 七、下一步线索（按可行性排序）

1. **补对照组数据，而不是继续猜**。把真实模式按「只改一处」拆开测：拿 猪猪钩钩乐·原版.ow，
   分别删掉全部 320 个块 / 全部 51 个三元 / 全部 `事件玩家`，各导入一次读元素数。三个差值就能
   把上面「每条都能被否掉」的死结解开。这条路成本最低（每份 5 分钟），比逆向 55 MB 靠谱。
2. **`事件玩家` 到底是变量还是常量**：它是事件上下文里的玩家引用，模型里当常量记 1。如果游戏把它
   当成"要额外一条取值元素"，577 次就是 +577，是当前最大的单一嫌疑。
3. **二进制续做**：`0x3346018` 那个 `cmp [r14], 0x18800` 的函数值得往上追调用者（它的上层很可能
   就是「诊断面板」的组装函数）。追法：从 `.pdata`（异常表，0x5725000 起）反查函数边界，按
   RUNTIME_FUNCTION 的 BeginAddress 建函数表，就能把「函数 → 地址区间」做准，再对 32768 的 451
   个立即数按函数归类，找「函数内同时有 98 KB 或 12 或 32767」的那一个。`.pdata` 有 0x24e600 字节，
   约 3.9 万条记录，覆盖全部函数——这是绕开 IDA 缺 xref 的标准做法。
4. **不要再指望字符串**：工坊名字表在 CASC 语言包里，exe 只有 ID。要按名字找，得先解 CASC。
