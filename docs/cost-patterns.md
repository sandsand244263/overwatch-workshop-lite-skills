# 省元素的手法（带着镣铐跳舞）

> 元素上限 32768、单条规则约 98KB。这份文档只讲**同样效果怎么写更省**。
> 每条都标注来源：**实测**（探针导入验证过）/ **推导**（由 25/25 元素公式算出）/ **经验**（作者实战总结，未单独验证）。

---

## 一、把数字字面量换成"恒定的值"（经验 + 推导，最实用）

死斗这类模式不跑回合，于是有几个值恒等于常数：

| 值 | 恒等于 | 说明 |
|---|---|---|
| `比赛回合` | **1** | 不跑回合的模式永远是第 1 回合 |
| `比赛结束` | **0** | 等于"处于回合之间" |

```
事件玩家.A[1] = 事件玩家.A[比赛回合]      // 效果一样，省 1 个元素
```

**为什么省**（用 25/25 标定的估算器实测对比）：

```
伤害(事件玩家, 事件玩家, 1);          →  3 元素
伤害(事件玩家, 事件玩家, 比赛回合);    →  2 元素     省 1

伤害(事件玩家, 事件玩家, 0);          →  3 元素
伤害(事件玩家, 事件玩家, 比赛结束);    →  2 元素     省 1
```

原因：数字字面量 = `数值()` 1 + 字面量 1 = 2，顶层参数减 1 后是 **1**；值函数本身 1，顶层参数减 1 后是 **0**。**每次替换省 1 个**。一处不显眼，几百处就是几百个。

**附带好处：混淆**。读代码的人看到 `比赛回合`，第一反应是"这跟回合有关"，不会想到它其实是个 1。这条正好和 `publish.py` 的混淆功能叠着用。

⚠️ **前提**：只在"不跑回合的模式"里成立。团队模式里 `比赛回合` 会变成 2、3，替换就错了。

## 二、合并重复动作（经验）

同一段条件里，好几个动作共用同一个前置判断时，用嵌套把它们收进一层，避免重复写条件。

```
优化前：三处各写一遍 if(生命 < 50)
优化后：外层 if(生命 < 50) 一次，里面做三件事
```

**省的是条件**，不是动作。条件里的比较运算符单价很高（含比较条件固定 +3）。

## 三、初始化放最上面（经验）

`设置受到伤害` 这类"设定初始状态"的动作要放在规则最前面，后面再用条件覆盖。放到最后是写法错误——中途受伤的玩家拿到的百分比是错的。

这条不省元素，但**省调试时间**。

## 四、布尔与数字的关系（经验，容易踩）

- `!0 = 真`
- `1 = 比赛回合`，**1 属于真，但不等于真**
- 判断"等于真"和"非零"不是一回事，写条件时别混

## 五、数字精度上限（经验）

- **带小数点**：只能显示 4 位（如 `0.1234`）
- **不带小数点**：约 12 位

超过上限的值，导入后再复制出来会**变成 0**——这是"代码看着对、跑起来是 0"的常见来源。

## 六、字符串插值别拆（推导）

`自定义字符串("连杀 {0}！", A)` = 5 + 1 个插值 = 6 元素。

拆成 `自定义字符串("连杀 ") + A + 自定义字符串("！")` 并不会更省——每个字符串各 5 元素，还要加拼接。**一条带插值的字符串永远比拆开便宜。**

## 七、HUD 刷新用"改文本"而不是"重建"（实测）

同一个玩家、同一个位置创建 HUD，游戏会自动刷新那一条，不会堆叠。但每次仍要付 `创建HUD文本` 的成本（12 元素）。

循环里连续刷新时，**能算好一次再赋值，就不要每次重建**。

## 怎么用这份文档

写模式时，先按常规写对，再回头做两件事：

1. **数字扫一遍**：`1` 和 `0` 在不跑回合的模式里，能换成 `比赛回合` / `比赛结束` 就换
2. **重复条件扫一遍**：同一条件出现两次以上，考虑嵌套合并

然后跑 `python tools/ws.py count <文件>` 看省了多少。
