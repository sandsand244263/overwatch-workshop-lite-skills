# 避坑：导出与工程纪律

> 导出失真怎么修、校验器怎么维护（工程纪律）。

> 总索引见 [pitfalls.md](./pitfalls.md)；报错原文查 [errors.md](./errors.md)。

## 三层检查（2026-10-22）：格式对了也可能导不进去

格式层全绿只说明"语法像工坊"，**名字过时、槽位类型错**一样导不进去，而且游戏给的报错完全指不到根因。
现在校验器多查两层，写模式时按这个顺序自查：

1. **格式层**：括号 / 分号 / 参数个数 / 事件参数个数 / 值函数当动作 …
2. **数据 ID 层**：地图 / 英雄 / 技能 / 按钮 / 设置键 / 事件名 必须存在于 `data/` 的当前版本表
3. **类型层**：玩家槽别塞数字、数值槽别塞玩家、子程序调用必须有声明、单条规则 ≤ 98KB、总元素 ≤ 32768

文案统一是 `X「Y」不在当前版本数据表里（可能已改名或移除）`——**看到这句就是版本差异，不是语法错**。

| 坑 | 表现 | 正确做法 |
|---|---|---|
| 地图名过期 | 报「"地图("之后应有一个地图名称」 | `ws.py maps` 查当前 291 个有效名 |
| 英雄名过期 | 报「"英雄("之后应有一个英雄名」 | 对照 `data/heroes.tsv`（54） |
| 技能名过期 | 英雄设置键报「之后应有一个…」 | `data/abilities.tsv`（名字 + 所属英雄） |
| 设置键改名 | 报「"开启"之后应有一个游戏模式设置」 | `ws.py settings --mode <模式>` 生成合法键 |
| 事件名过期 | 报「之后应有一个队伍」 | `data/events.tsv`（14） |
| 玩家槽塞数字 | 报「之后应有一个玩家」 | `设置移动速度(本地玩家, 120)` |
| 数值槽塞玩家 | 导入失败或行为诡异 | 数值槽要 `数量(玩家)` / `生命值(玩家)` 这类取值函数 |
| 子程序没声明 | 报「未知的子程序」 | `调用子程序(X)` 前先在 `子程序` 块登记 |
| 单条规则超 98KB | 诊断面板「每条规则长度不得超过98KB」 | 一条规则塞太多动作就拆开，别指望游戏帮你数 |
| 元素数超 32768 | 诊断面板「总计元素数量」 | `ws.py count` 估算，大文件乘 2.12 |

**技能名在 .ow 里只出现在英雄设置键中**，两种形态（括号内 / 空格后）：

```
终极技能充能速度（鸡飞狗跳）: 100%
战斗时终极技能充能速度 鸡飞狗跳: 34%
```

英雄设置键**不要**自己拼技能中文名——技能改名是版本更新里最常见的一类破坏。

**行号保真**：跨行语句报错会指到内容真正所在的那一行，不是语句起始行。
看到报错行号时按"原文那一行"去数，别按你脑子里的合并后逻辑数。

## 校验器自己也会骗人（2026-10-22 复盘）

`strip_noise` 逐行处理，但被喂了**整篇文本**——它在第一个 `//` 处 `break`，于是所有基于
masked 文本的检查其实只看得到文件开头几行。真实模式长期"0 报错"，一半是这个 bug 遮出来的。

修法：`mask_text` 做**等长遮罩**（字符串 / 注释换成空格，长度和换行都不变），
既能全文扫描，又能用列偏移查 `SegMap` 换算行号。

**教训**：校验器"全绿"时必须拿真实文件反证一次；换实现（这里是 strip_noise → mask_text）
之后，误报会一次性涌出来——那才是真实覆盖面。修掉 6 类误报后才算真的全绿。

## 生成类工具必须独立复校（2026-10-22）

**规则**：任何「生成/改写文件」的工具（混淆器、批量生成器、模板填充），产物都要由**另一套代码**重新校验一遍，不能信生成器自己的自检。

两个真实案例，都是产物无法导入、而工具自己以为成功：

| 工具 | bug | 为什么自己的自检没发现 |
|---|---|---|
| `obfuscate_values` | 按旧字符串下标做替换，文本变长后位置错位，`全局.LifeguardX方向分量` 被切成 `全局.LifeX方向分量` | publish 自检只传了 `event_params` 一张表，比 `check` 弱，这一类名字错误根本不在它的检查范围内 |
| `obfuscate_indexes` | `("%f" % 0).rstrip("0")` 把 `0.000000` 削成 `0.`，写出非法数字 | 同上 |

修法有两条，缺一不可：

1. **统一校验入口**：`core.full_lint()` 同时被 `ws.py check` 和 `publish` 调用，杜绝「两套检查强度不一致」
2. **独立冒烟测试**：`tools/selfcheck_publish.py` 造样本 → 生成 → **再独立跑一遍 full_lint**，不复用生成器的结论

**同类教训**：`strip_noise` 在第一个 `//` 处 break，导致所有基于遮罩文本的检查只看得到文件开头——校验器自己坏了，所有「通过」都是假的。

判断一个检查器是否可信，只看一件事：**它读完了整个文件吗？它跑的是完整规则集吗？**

## 导出会失真，导入前先归一化（2026-10-22，四个真实模式验证）

拿 4 个真实模式（275–413 KB，150–213 条规则）跑校验器，暴露了导出与编辑器之间的差异：

| 现象 | 说明 | 处理 |
|---|---|---|
| 某些位置写「无」 | 编辑器里是「全部禁用」，导出写成「无」 | `ws.py normalize` 自动改回 |
| 变量声明缺失 | 导出后 `全局.X` 有引用、`变量` 块里没有声明 | 只警告（无法可靠重建索引） |
| 长语句折行 | 导出把一条语句拆成多行 | `normalize` 会合并（含字符串内换行保护） |
| 地图/设置键查不到 | `万圣节吉拉德堡`、`圣诞节生态监测站`、`开局符文刷新次数` 等 | 数据表缺这些变体/模式专属键，按「可能缺项」提示 |

**结论：导出的 `.ow` 不能当规范**，只能当「能读懂的内容」。要拿去重新导入，先跑：

```bash
python tools/ws.py normalize 导出.txt -o 修好的.ow
```

`normalize` 做三件事：合并折行语句（跳过 `变量` / `子程序` 块）、把特定位置的「无」改成「全部禁用」、输出后自动再校验一遍。

**注意**：`变量` 块声明丢失、地图/设置键的变体名，`normalize` **不会瞎补**——补错比不补更糟。

## 导出失真的四种类型与修法（2026-10-22，四个真实模式验证）

四个真实模式（137–413 KB）在游戏里逐个导入验证，结论：

| # | 失真 | 表现 | 能否自动修 | 已实现 |
|---|---|---|---|---|
| 1 | 「无」进了要求「全部禁用」的位置 | `不要截取, 无` 被拒 | ✅ 能，位置固定 | `normalize` 默认 |
| 2 | 设置值被吞掉 | `招架姿态恢复倍率:` 后面空着 | ⚠️ 只能删行（用默认值） | `--drop-empty` |
| 3 | 布尔词写成界面词 | `目标点决胜机制: 禁用` 被拒 | ⚠️ 按类型判断，个别模式接受「禁用」 | `fix` 默认 |
| 4 | 键写错层 | `复生时间` 写进 `决斗先锋`（它属于「英雄」层） | ❌ 需要归属表，只报不改 | `check` warning |

**实测记录**

| 模式 | 需要修什么 | 导入 |
|---|---|---|
| 下100层 | 无 → 全部禁用（7 处） | ✅ |
| 符文乱斗 | 无 → 全部禁用（2 处） | ✅ |
| 丧尸守桥 | 布尔词（54 处 Bool 键） | ✅ |
| 找蛋躲猫猫 | 无（24 处）+ 空值行（3 行）+ 布尔词（4 处） | ✅ |

## 改校验器之后必须跑的三件事（2026-10-22）

```bash
python tools/ws.py selftest     # 有没有同名函数重复定义（后定义的静默生效）
python tools/ws.py check-all    # 65 正样本 + 21 反向用例
python tools/ws.py corpus       # 4 个真实模式（私有语料）
```

前两个查「自己写的东西还对不对」，第三个查「真实文件会不会冒出新误报」。

**为什么必须有第三个**：65 个自写样本全绿、真实文件一跑就冒出 12 个误报（2026-10-22 实测）。
自写样本只能验证「按我的假设写的代码」，验证不了「别人的写法」。

真实语料不在本仓库（是他人作品，不公开）；维护者本机用环境变量 `WS_CORPUS` 或技能根的 `local_paths.json` 指过去。

## 面向大众的三条底线（2026-10-22）

| 命令 | 解决什么 |
|---|---|
| `ws.py doctor` | 出问题时先分清「环境问题」还是「文件问题」 |
| `ws.py report 文件` | 误报/漏报时生成脱敏的最小复现，直接贴 issue（引号内容全换 `…`，模式名/描述/规则名/字符串正文都不带出去；路径里的用户名换 `<user>`） |
| 自动识别编码 | 用户把文件存成 ANSI(GBK) 也能读，不崩、不报乱码错 |

**编码**：`core.read_text()` 依次试 UTF-8-sig / UTF-8 / GB18030 / UTF-16，返回实际编码。
中文用户用记事本存文件默认是 ANSI(GBK)，按 UTF-8 读会直接抛 `UnicodeDecodeError`——这是新用户最容易一上来就失败的地方。

**report 的脱敏**：长字符串内容换成 `…`，只保留结构；变量名、设置键保留（它们是定位问题的关键）。
