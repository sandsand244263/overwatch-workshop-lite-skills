# 生态：周边工具怎么配合

工坊这块的能力是分层的，本 skill 只管"写对"，其余交给下游工具。

## 一、分工表

| 工具 | 管什么 | 什么时候用 | 注意 |
|---|---|---|---|
| **本 skill（WorkshopLite）** | 写：语法、参数、枚举、设置项、格式校验 | 从想法到生成可导入代码 | 生成后必须跑 `tools/ws.py check` |
| **VS Code 插件**（xhanl/overwatch-workshop） | 补全、跳转、格式化、导入导出、**混淆** | 手工改代码、要 IDE 体验、发布前做混淆 | 见下面第二节 |
| **workshop.codes** | 在线编辑器、linter、代码分享、社区模式 | 想参考别人的实现、想让别人在线看/复制 | **只解析英文语法**，不能校验中文 `.ow` |
| **overpy** | 高级语言 ↔ 工坊代码（编译/反编译） | 想读懂一大坨被人混淆过的代码、想用 Python 风格写 | 反编译出来是 .opy，不是 `.ow` |
| **OWLib / DataTool** | 从游戏本体导数据（元素、枚举、字符串、设置项） | 游戏更新后同步数据 | 导出前必须关闭游戏与战网 |

## 二、VS Code 插件的混淆功能（5 项）

命令名 `ow.command.obfuscate`，运行前会让你填**原生代码的元素总数**（地图工坊 → 显示诊断结果 → 总计元素数量；上限 32768）。可勾选：

| 选项 | 做什么 | 副作用 |
|---|---|---|
| 混淆规则 | 填充虚假规则 | 占元素额度 |
| 混淆变量 | 变量/子程序名改成不可读文本，并填充假变量 | 自己后续维护会很痛苦 |
| 混淆字符 | 隐藏字符串内容 | **影响字符串比较**（比如比对玩家名）。用 `/* @SKIP_OBFUSCATE_STRING */` 和 `/* @SKIP_OBFUSCATE_STRING_END */` 包住要保留的部分 |
| 混淆索引 | 把二次复制的代码索引数值打乱 | 影响服务器负载 |
| 混淆本地索引 | 本地索引数值不可读 | 影响客户端帧率 |

### 混淆颗粒度对照（我们的脚本 vs 插件）

| 手段 | `publish.py --obf` | 插件 | 说明 |
|---|---|---|---|
| 数值改写（插件没有） | `numbers` | — | 等价表达式，不改语义、不掉性能 |
| 混淆变量 | `vars` | ✓ | 改名 + 引用同步 |
| 混淆规则 | `rules` | ✓ | 追加永不触发的假规则 |
| 混淆索引 | `indexes` | ✓ | `[n]` → `[乘(10000000, …)]` |
| 混淆本地索引 | `local-indexes` | ✓ | 同上 |
| 混淆字符 | ✗（改用插件） | ✓ | 会改变字符串比较语义，脚本不碰 |

**默认不出混淆版**：用户没提混淆就只出源码版，别自造第二份文件。要混淆时按上面的名字显式指定。

**建议用法**：混淆是**发布前**的最后一步，不是写代码时做的事。

1. 先在本 skill 里生成干净的、可读的 `.ow`，跑 `tools/ws.py check` 通过
2. 存一份原文件（混淆后基本不可逆，改功能要从原文件改）
3. 再用插件混淆，导出发布版
4. 混淆后**不要**再用 `tools/ws.py check` 判断逻辑——它会读到一堆假规则和混淆数值

## 三、什么时候用 overpy

- 拿到别人的模式，看不懂：反编译成 `.opy`，读逻辑比读 `.ow` 快
- 想写复杂逻辑（数组循环、函数复用）：用 overpy 写，编译成工坊代码
- 但它生成的是它自己那套 `.ow` 排版，和我们的格式规范不同，两者不要混着改

## 四、workshop.codes 的定位

- 它**能**校验英文语法的工坊代码（括号、参数个数、尾逗号、条件比较、事件参数、变量大小写等），规则和我们的 linter 有交集
- 它**不能**校验中文 `.ow` —— tokenizer 只认 `settings/variables/rule/event/actions`
- 所以：当参考和分享平台用，不要指望它替你验中文代码
