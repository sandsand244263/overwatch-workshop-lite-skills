# ADR-0002 · `check` 的结论改三态（必改 / 已验 / 未验）

## Status

`Accepted（决策 2026-11-03；v3.38.0 起生效）`

## Context

**项目由单人 + AI 维护，无代码评审环节**——这是所有取舍的前提。

旧输出是二值语气：没 error 就打印「✓ 可以导入」。问题在于这个结论**本地根本证不了**：

- 唯一权威是游戏本体。本地校验只能证明「没命中 87 条已知模式」，证明不了「游戏接受」。
- 8 千行真实文件 `check` 只要 4~5 秒，看起来像验完了，实际覆盖面是「已写过的检查」而不是「这个文件的所有写法」。
- 已发生的两次事故都出在这里：v17 的探针文件 `check` 全绿、实际导入被拒；#13 的追加写法在模型里合法、
  在引擎里拆包。用户看到「✓ 可以导入」就不再往别处想，错误信号被我们自己的文案吃掉了。

不改的代价：每一轮都要靠人记得提醒「check 绿只是必要条件」，而这句提醒进不了输出，
读输出的使用会话（和下一个 AI 会话）永远只看到「可以导入」。

## Decision

`check` 的结论改成三态，并把「这次没验什么」写进同一条输出：

```text
✓ xx.ow：没发现必改问题（已验 87 条 / 未验 2 类）
  未验：跨行字符串里的引用、元素数真实值
  提示 3 条（不影响导入）
```

1. **已验 N 条** = 本次实际跑的 `check_*` 数量，从自检名单算，**不许写死**（检查增删后自动跟着变）。
2. **未验 K 类** 从 `data/coverage-gaps.tsv` 读，每条 gap 必须有「触发判据 + 文案」，且必须指向
   一个**已经发生过**的 issue 或实测记录——写「可能不准」的 gap 一律不收。
3. 有 error 时输出**不变**（必改优先，先给能动手的）。
4. `--json` 加 `"coverage": {"checked": N, "gaps": [...]}`，让编辑器与 CI 拿到同样信息。

明确不做：**不删检查、不改判定阈值**。这一条只改「说法」，不改「查什么」。
也不把「可以导入」换成另一种断言（「保证能导入」），那只是换个方向撒谎。

## Consequences

- 输出从「结论」变成「结论 + 边界」。用户拿到的是可以行动的两句话：改这几条 / 这几类要导入一次看。
- 免责清单有变成噪音的风险：gap 超过 4 条就重想——说明书写给谁看都不读，输出里堆条件等于没有输出。
- 代价：`coverage-gaps.tsv` 是**手工表**（没有生成器），条数只能靠人克制。规矩写进表头：
  每条 gap 必须能指向已发生的 issue 编号或 E 编号。
- **这一版还没变的东西**：底层 `check_*` 一条没动（87 条），`--strict` 语义不变；
  「能不能导入」的最终判据仍然是游戏，这一条 ADR 只保证我们不再假装自己知道答案。

## Evidence

```text
# 旧口径（v3.37.3 及之前）
python tools/ws.py check <file>.ow   → ✓ 没发现必改问题        ← 结论是二值的

# 新口径验收（v3.38.0）
python tools/ws.py check <file>.ow   → ✓ 没发现必改问题（已验 87 条 / 未验 2 类）
python tools/ws.py check-all         → 正 93/93、反 98/98（结论改动不许动回归读数）
python tools/check-all 的 --json      → 带 "coverage": {"checked": 87, "gaps": [...]}
```

gap 表的四条触发判据（每条都对应已发生的 issue）：跨行字符串（#1/#17）、引擎运行期语义（#13）、
元素数真实值（#14 口径分裂）、语料里没见过的写法（#17 的第五处）。
