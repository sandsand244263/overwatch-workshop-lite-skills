# ADR-0000 · 模板（复制这一份，别改它）

> 什么时候才写 ADR：**只认两条硬判据**，满足其一才写，其余一律写 `CHANGELOG.md`。
>
> 1. 改变**对外输出语义**（例：`check` 的结论从「可以导入」改成「已验 / 未验」）。
> 2. 换掉**一层实现**（例：正则 + 按行处理 → 语句切分）。
>
> 不设「每个结构级版本必须有 ADR」这种断言——那只会催生凑数的 ADR。
> 历史决策 `D-001..D-0xx` 留在私有仓 `DECISIONS.md`，不迁移。

---

## Status

`Proposed` / `Accepted` / `Deprecated` / `Superseded by ADR-XXXX`。带上生效版本与日期，
例：`Accepted（v3.37.3，2026-11-03）`。

## Context

为什么现在必须做这个决定：读者是下一个 AI 会话，要能看懂当时的约束，而不是复述需求。
写清三样：**问题形状**（同一个根造成了几次 bug）、**已有实现为什么挡不住**、**不改的代价**。

## Decision

一句话说清改了什么，再列具体边界（做什么 / 明确不做什么）。不写实现细节，
实现细节归 `CHANGELOG.md` 与代码注释。

## Consequences

好的、坏的都写。至少一条「这一版还没变的东西」，防止下个会话以为已经做完了。
坏的一条最容易漏：多出来的维护成本、被放弃的能力、需要人盯的地方。

## Evidence

**必须可复现**：命令 + 当时的读数（条数、耗时、文件名）。写「已确认 / 逻辑合理」不算证据。
读数会随版本变，所以要带版本号与日期。

## Supersedes

被本条取代的旧决定（ADR 编号或 `DECISIONS.md` 的 `D-0xx`），没有就写 `—`。
取代关系只追加：旧条目不删、不重排，只在它的 Status 里加一行 `Superseded by ADR-XXXX`。
