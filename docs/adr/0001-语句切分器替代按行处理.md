# ADR-0001 · 用语句切分器替代「正则 + 按行」

## Status

`Accepted（v3.37.3 铺底座，2026-11-03；改写搬迁在 v3.38.0 收尾）`

## Context

**项目由单人 + AI 维护，无代码评审环节**——这是所有取舍的前提：没有人在 review diff，
所以「哪里会错」必须由结构本身保证，不能靠人记得看一眼。

问题形状：三周内五条 issue 是同一个根，散的看起来像五个无关的 bug。

| issue | 表面症状 | 根 |
|---|---|---|
| #1 | 跨行字符串被当成语法错误 | 逐物理行判断引号状态 |
| #4 | 跨行数组里的注释让后续所有语义检查静默失效 | 遮罩按行切，状态不跨行延续 |
| #8 | 带 `//` 注释的声明漏改名 | 声明识正则撞上行尾注释 |
| #17 | 跨行字符串后面的变量引用漏改名 | 改名只扫「行」内的 token |
| #17 修复时撞到 | 删查看器动作后留下断引号 | 靠数括号深度找收尾 `;`，跨行时找错 |

已有实现挡不住的原因：`core.py` 里早有 `join_multiline_strings_mapped` / `merge_continuations_mapped` /
`mask_text` / `line_sections` 这些文本工具，但**只在 `lint()` 内部用**，`publish.py` / `obf_parts.py`
一处都没用，各写各的 `text.split("\n")`。同一个「语句在哪结束」的问题有 N 份实现，N 就是 bug 数的下界。

不改的代价：每修一条跨行 bug 都要在 4 个模块里各补一次特判，而语料里**跨行字符串 0 处**
（9 份、58,335 行），意味着这类 bug 在本仓库永远不会被回归抓出来——只能等用户导入失败。

## Decision

在 `tools/core.py` 加一层 `split_statements(text)`：整份 `.ow` → 语句单元，
每单元带 `start/end`（字符偏移，首尾相接等于原文）、`line_start/line_end`（1 基）、
`kind`（`statement` / `block_header` / `brace` / `block_line` / `blank` / `comment`）、
`code`（本单元里属于代码的绝对区间，字符串与注释已剔除）。

之后**所有**「一条语句从哪到哪」的判断只准问它：检查、改名、删动作、清规则名、计数。
改写类模块只在 `code` 区间内动，字符串与注释区间永不触碰。

明确不做：不写完整表达式解析器。只认四类单元 + 深度 0 的 `;`，够用即停（完整语法树是另一个项目）。

## Consequences

- 跨行类 bug 的修法从「四处补特判」变成「一处改切句器」，回归也只需要测切句器一条。
- `tools/selfcheck_statements.py` 成了结构层的外部判据：9 份语料 + 全部探针必须**逐字节还原**
  （`"".join(text[s.start:s.end] for s in stmts) == text`），切漏一个字符当场红。
- 代价：切句器本身成了关键路径，它错则所有下游一起错。所以它必须配自检，且自检要独立于实现
  （用原文还原，而不是用切句器自己的字段互证）。
- **这一版还没变的东西**：v3.37.3 只铺底座，`rename_vars` / `strip_viewer_actions` / 注释清理 /
  规则名清理四处改写仍在用旧写法（v3.38.0 才搬）；`check_*` 条数不变（87）。


**跨行字符串 0 处**——这就是这类 bug 长期潜伏的原因，补语料样本是 v3.38 之后的任务。
