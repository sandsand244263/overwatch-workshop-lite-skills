## 工坊执行机制（实测 2026-10-20；2026-10-23 用 8 格矩阵 + 条件翻转复核）

**一句话模型：规则在「条件由假变真」的那一刻执行一次。没有条件 = 一开始就是真 = 开场执行一次，之后不再执行。**

### 常量条件（`M_持续行为矩阵.ow`，每秒打点）

| 格子 | 结构 | 8 秒后的计数 |
|---|---|---|
| c1 | `持续 - 全局`，无任何条件 | **1** |
| c2 | `持续 - 全局` + 动作里 `If(1 == 1)` | **1** |
| c3 | `持续 - 全局` + 动作里 `If(1 == 2)` | **0** |
| c4 | `持续 - 每名玩家`，无条件 | **1** |
| c5 | `持续 - 每名玩家` + `If(1 == 1)` | **1** |
| c6 | `持续 - 全局` + `While(真)` + `等待(0.1)` | **144**（每秒 +9） |
| c7 | `持续 - 全局` + `等待(0.1)`（不循环） | **1** |
| c8 | `持续 - 每名玩家` + `等待(0.5)` | **1** |

### 条件翻转（`D_条件翻转.ow`，条件写在 `条件` 块里）

| 时间 | 发生什么 | 读数 |
|---|---|---|
| 3s | `flagA` / `flagB` 由 0 变 1 | d1=0 d2=0（这一帧还没轮到执行） |
| 4s | 条件假→真 | **d1=1 d2=1** ← 上升沿触发 |
| 4s | `flagB` 落回 0 | d2 保持 1 |
| 6s | `flagB` 再变 1 | — |
| 7s | 第二次上升沿 | **d2=2** ← 每次上升沿各触发一次 |
| 全程 | `flagC` 永远 0 | **d3=0** |

### 由此确定的写法

- **「条件成立时做一次」→ 把条件写进 `条件` 块**，不用 `While`。条件每满足一次（上升沿）就跑一次。
- **「持续做事 / 定时刷新」→ 必须 `While(真)` + `等待`**（c6）。只加 `等待` 不算循环（c7/c8）。
- 条件一直为真期间**不会重复执行**（c2=1），别指望用它做轮询。
- 推论：HUD 刷新、计时器、状态检测一律走 `While(真)` 模板；伤害/击杀/按键这类直接绑事件。

## 每名玩家 = 每人一个实例（`P_每名玩家口径.ow`，两人在场；E-49）

| 格子 | 结构 | 12 秒后 |
|---|---|---|
| c1 | 每名玩家，无条件 | **2**（一人一次；机器人中途加入时补了一次） |
| c2 | 每名玩家 + 条件 `flagA == 1`（第 3 秒抬起） | **2** |
| c3 | 全局 + 同一条件（对照） | **1** |
| c4 | 每名玩家 + `While(真)` + 等待 0.5 | **66**（+4/秒） |
| c5 | 全局 + `While(真)` + 等待 0.5（对照） | **42**（+2/秒） |
| c6 | 每名玩家 + `If(1 == 2)`（对照） | 0 |

- **每名玩家 = 每人一个实例**，不是「整条规则只跑一次」。后加入的玩家会补一个实例（日志里机器人在 00:00:08 才补了 `[P1]`）。
- **条件上升沿、`While` 循环、玩家变量都是实例私有的**：同一时刻抬一个全局开关，两个实例各触发一次（c2=2 / c3=1）；每个人有自己的循环（c4 是 c5 的两倍）。
- 所以「每名玩家」里写的计数器**不用除以人数**——`全局.x = 全局.x + 1` 加一次就是一个人头。想统计「多少人做过某事」直接累加即可。

补充：`持续 - 每名玩家` 在**加载期**就开始跑（本次 00:00:00 就为人类玩家触发了 `[P1]`），开赛要再等 8~11 秒。

## 死斗里 `队伍1` / `队伍2` 是空壳（2026-10-23 实测）

| 读数 | 值 |
|---|---|
| `数量(所有玩家(队伍1))` / `(队伍2)` | 0 / 0 |
| `栏位数量(队伍1)` / `(队伍2)` | 0 / 0 |
| `数量(所有玩家(所有队伍))` | 2 |

- 死斗里玩家既不在 队伍1 也不在 队伍2 → `生成机器人(英雄(死神), 队伍1, …)` **没有槽位，静默失败**（不报错、不出现）
- 塞机器人必须写 **`所有队伍`**；位置/方向可以写 `空`，游戏自己找出生点
- 推论：死斗里遍历玩家一律用 `所有玩家(所有队伍)`，按队伍取会拿到空数组

## 事件规则是单实例：忙的时候事件会丢（`R_事件重入.ow`；E-50）

| 结论 | 读数 |
|---|---|
| 一次 `伤害()` = **一次**「玩家受到伤害」事件 | 每次打点时计数器 +1（打 5 点和打 1000 点都一样） |
| 事件规则**同时只有一份执行**：正在 `While` 里忙时，新事件被**丢弃**（不排队、不重入） | t=2 进入、t≈4.5 退出；t=4 那次事件这条规则没接，t=6 才再次进入 |
| 不同规则互不影响 | 同一个伤害事件：忙的那条规则丢，闲的那条正常 +1 |
| 自伤致死**触发「玩家阵亡」一次**，但**不算「造成最后一击」** | 阵亡计数 1 / 最后一击计数 0 |
| 死亡期间打伤害**不产生事件** | 死亡后连续打点三次，伤害事件计数停在 4（单次观察，未复核） |

**写法**：事件规则里只放「立刻能做完的事」。要慢慢处理就拆开——事件里只记标记（`全局.有活 = 真`），
把循环放到**另一条** `持续 - 全局` 的 `While` 里轮询。想让同一事件排队，工坊没有队列，只能自己用数组做。

## `本地玩家` 当动作目标：部分动作无效（2026-10-23 实测；2026-10-24 修正说法）

在 `持续 - 全局` 规则里，下面这几个动作对 `本地玩家` **实测没有任何效果**（不报错、不生效）：

| 动作 | 现象 |
|---|---|
| `隐藏英雄HUD(本地玩家)` / `隐藏游戏模式HUD(本地玩家)` | 屏幕照旧，角色和 HUD 都在 |
| `开始镜头(本地玩家, …)` | 镜头不动 |
| `伤害(本地玩家, 本地玩家, 5)` | 血不掉，伤害事件也不触发 |

**但不要说「本地玩家 在这里是空的目标」**——那是过度概括。8 份真实语料里有 **197 处**把 `本地玩家` 当参数写进 `持续 - 全局` 规则，
而且这些模式在游戏里正常工作（`创建HUD文本(本地玩家, …)`、`已过滤的数组(本地玩家, …)`、`距离准星最近的玩家(本地玩家, …)`）。

所以现在的准确说法：**`本地玩家` 本身能用，但「动到玩家身体/视角」的那几个动作在全局规则里吃不到它**，原因未定。

**根因（官方原文，2026-10-25 对上）**：`生命值`/`最大生命值` 这类**属性读取**在 `持续 - 全局` 里对 `本地玩家` 一律返回 **0**
（探针 `lab/runtime-r3` 第 12~21 秒连读 10 次全 0），而同一秒 `持续 - 每名玩家` 里读 `生命值(事件玩家)` 正常（250 / 300）。
官方对 `本地玩家` 的说明是：**「由终端用户的设备所操控的玩家……只有会影响视觉效果或 HUD 的动作才可访问此值。此值无法储存在变量中。」**
→ 所以「读属性 = 0」「存进全局变量报错」「`伤害`/`隐藏HUD`/`开始镜头` 没效果」是**同一条规则**的三个面，不是三个 bug。
语料里 76 处 `本地玩家` 全在 HUD 文案路径里（`所用英雄(本地玩家)`、`所在队伍(本地玩家)` 喂给 `创建HUD文本`），与这条说明一致。

写码含义：**`本地玩家` 只用来喂 HUD/视觉动作**；要读属性、要造成效果，一律走 `持续 - 每名玩家` + `事件玩家`。
校验器只判那三个「动身体/视角」的动作（`check_local_player_in_global`），**不判属性读取**——
语料里 65 处读属性全在 HUD 路径里、是合法用法，按行判会大面积误报。

顺带：`宣告玩家胜利(主机玩家)` 写在 `持续 - 全局` 里、等 30 秒触发，比赛**没有**结束（日志继续到 45 秒）——同类原因（非视觉动作访问 `本地玩家` 家族），改成 `持续 - 每名玩家` + `事件玩家` 即可。
稳妥写法：

- 探针隐蔽、自伤、镜头、藏 HUD → 写在 **`持续 - 每名玩家`** 规则里用 `事件玩家`（实测有效）
- 纯 HUD 文本、玩家过滤、距离计算 → `本地玩家` 可以照常用（语料实证）
- 要在全局规则里动所有人 → 写显式集合 `所有玩家(所有队伍)`

**待验证**：在 `持续 - 全局` 里 `记入查看器(自定义字符串("{0}", 本地玩家))` 能不能打出玩家名。能打出 → 说明是那几个动作挑剔；打不出 → 说明 `本地玩家` 在全局规则里确实没有值。一次读数就能定性。

## 等待 / 循环（实测 2026-10-20）

- `等待(时间, X)` 的 X 有三个合法词：`无视条件` / `当为“假”时中止` / `当为“真”时重新开始`，填条件表达式会报「之后应有一个选项」。
  （2026-10-24 实测：一个文件里三种各写一次，导入成功、三条规则都跑，查看器 `A=2 / B=2 / C=2` —— 三种都接受且等待都正常返回。
  依据：exe 槽位校验 `0x140C41860` 比较这三条文案的句柄 `0x787C/787D/787E`；9 份真实语料 1948 处第二参数全部落在这三个词里。）
  **注意**：挂条件列表时「中止 / 重新开始」的行为差异还没测。
- 条件等待要自己写循环：`While(全局.条件 != 真); 等待(0.1, 无视条件); End;`
- **`等待直到(条件, 超时)` 在 `持续 - 全局` 里真的会阻塞**（2026-10-25 读数，探针 `lab/runtime-r3`：
  第 5 秒把标志置真，规则在第 5 秒才继续，`a1=2 wait_t=5`）。**阻塞期间 `While` 的条件每轮都在重估**：
  同一次实测里 `While(标志 == 0)` 每 0.5 秒一轮，标志变真后循环立即退出（`b2=10 loop_t=5`，正好 5 秒 × 每 0.5 秒）。
  所以「等待直到堵住的循环」不会变成死循环——条件一到就散。
- `For 全局变量(i, 1, 5, 1)` 的终止值**不包含**：实际跑 1→4；控制变量必须先声明

## 数组 / 循环 / 事件（实测 2026-10-20 第二批）

- **数组追加**用 `修改全局变量(arr, 添加至数组, 值)`；`加` 是数值加法，会对数组求和（写成 `加` 结果是 6，不是三个元素）
- 变量初值是 `0`，追加后数组变成 `[0,1,2,3]`：长度比追加次数多 1，第 0 项是 0。要干净数组先 `设置全局变量(arr, 空)`
- `While(真)` 里 `If(条件); 中断; End;` **能跳出循环**（实测 c 停在 3）
- 自伤 `伤害(玩家, 玩家, 1000)` **会触发「玩家阵亡」事件**；玩家变量在阵亡后仍可读
- 开局有约 5 秒倒计时，期间规则已在运行；测时间相关行为要留 10 秒以上余量

## 死斗的「获胜得分」就是目标分数（2026-10-21 实测）

## 真实模式的五种写法（2026-10-21，用 235 KB 实战模式验证）

拿一个真实上线的模式（8 个版本、最大 286 KB）跑校验器，一次报 **565 个 error**——**全部是误报**。真实代码里有五种教科书上没有的写法：

| 写法 | 例子 | 处理 |
|---|---|---|
| 块注释标记 | `/* @SKIP_OBFUSCATE_STRING */` | 逐行剥 `/* */`，未闭合的块注释连带剥 |
| 字符串注释行 | 单独一行 `"普通模式"` | 剥成空串后跳过，不当条件 |
| 跨行条件 | `(甲 \|\|` 换行 `乙)==真;` | 括号未闭合就并到起始行，后续行留空 |
| 跨行字符串 | `自定义字符串("{0} ` 换行 `", 玩家)` | 字符串内允许直接换行，接回一行 |
| 子程序里用 `事件玩家` | `子程序; Sub;` + `施加推力(事件玩家, …)` | **合法**：子程序继承调用方的事件上下文 |

**铁律**：多行合并必须**只合并、不改写**。第一版合并时我顺手把字符串抹成了空串，导致行号错位、插值检查全失效——真实样本立刻暴露。

**护栏**：合并超过 60 行仍未闭合就放弃并还原。否则一个引号判错会把后面整个文件吞进一条语句（实际发生过，报错指到 1451 行，其实是 500 行之后才闭合）。

**回归样本**：`tools/probes/real-idioms.ow` 固化了这五种写法。

## 结束比赛的动作跟模式不匹配（2026-10-22 实测）

现象：查看器里明明显示了「宣布比赛为平局」执行了，**但比赛还在继续**。

原因：三个结束动作的适用范围是写死的，用错模式不会报错，只是没效果。

| 动作 | 生效范围 |
|---|---|
| `宣告玩家胜利(玩家)` | **只在自由混战（死斗）生效** |
| `宣告队伍胜利(队伍)` | 自由混战**无效** |
| `宣布比赛为平局()` | 自由混战**无效** |

所以给死斗做「时间到 → 平局」是做不到的，只能改成判某个玩家赢（比如击杀数最高者）。

校验器会提示（**提示级，不拦导入**）：`「宣布比赛为平局」在死斗里无效（官方：此动作在自由混战模式中无效）；游戏不会拦导入，但这个动作不起作用`。

**为什么是提示不是必改**：v13 实机读数（E-84，探针 `c3-end-in-ffa.ow`）——死斗里写 `宣告队伍胜利(队伍1)`，游戏**导入成功**、规则继续执行（两条查看器行同一秒打出），只是这个动作不起作用。所以「导入会被拒」这个说法不成立，别为了让校验器拦住它去改文件。

**另一个坑**：房间默认「比赛人满后」开始。单人测试时比赛根本没开始，倒计时跑完也不会触发结束动作。测试文件应在 `综合` 块里写 `游戏模式开始: 即时`。

## 开局倒计时会吃掉你的计时（2026-10-22 实测）

现象：一个「每秒 +1 分、30 分获胜」的模式，开局刚打就赢了。数一下发现**比赛开始前已经攒了约 19 分**。

原因：`持续` 规则在**加载和开局倒计时期间就已经在跑**。死斗开局有约 5 秒倒计时，加上加载，实测能白跑 10 秒以上。

**做法**：持续类规则开头先等比赛真正开始。

```ow
动作
{
	等待直到(正在设置 == 假, 60);      // 等加载/准备阶段结束
	等待(6, 无视条件);                 // 再避开开场倒计时（实测约 5 秒）
	While(真);
		等待(1, 无视条件);
		…
	End;
}
```

- `正在设置`：此比赛是否正在准备阶段 → 加载结束变「假」
- 后面的 `等待(6)` 是给开场倒计时留的余量；不同模式倒计时长度不同，宁可多等
- **事件驱动的规则不受影响**（击杀、受伤只在开局后才会发生），不用加守卫

三个可运行样例与 `模式_抱团得分.ow` 现在都带这段守卫。

## HUD 播报不能当计数器（2026-10-22 用户实测）

现象：一个每秒 +1 分的模式，界面上的 `大字体信息` 看着只到 16 就宣布胜利了。

真实日志：

```
[00:00:44] [诊断] 分数=30
[00:00:44] [诊断] 触发胜利，分数=30
```

**引擎每秒 +1、到 30 触发，完全正确**。是 HUD 的问题——`大字体信息` 有动效，跟不上每秒一条，界面显示的是最后一条播完的旧值。

**做法**：

| 用途 | 用什么 |
|---|---|
| 测试、验证数值 | **`记入查看器`**（无动效、可一键复制、带时间戳） |
| 给玩家看 | `大字体信息` / `小字体信息`，但**别指望它实时** |

这条本来就写在 `docs/diagnostics.md` 里，这次是又一次验证：**测数值一律用查看器**。

## 循环里宣告胜负后要退出

```ow
While(真);
	…
	If(事件玩家.Score >= 30);
		宣告玩家胜利(事件玩家);
		中断;                 // 不写这句，每秒会重复宣告一次
	End;
End;
```

实测日志里 30 分之后每秒都记一条「触发胜利」，因为循环还在跑、条件仍然成立。

校验器会给 warning：`循环里宣告胜负后没有 中断 / 返回，会每秒重复宣告一次`。

## 想显示实时数值怎么办（2026-10-22）

`大字体信息` / `小字体信息` 是有动效的瞬时播报，**跟不上每秒一次的刷新**（实测每秒一条时，界面显示会落后很多）。

三种做法，按可靠性排：

| 做法 | 状态 | 说明 |
|---|---|---|
| **刷新降到 2-3 秒一次** | 未实测，但从动效时长推断可行 | 最省事；多数玩法不需要每秒变 |
| 用 `创建HUD文本` 的「重新赋值」参数更新同一条 | **未实测** | 该参数存在（`可见和字符串 / 字符串 / …共16项`），但没有验证过“同一条文本原地更新”的写法 |
| 只在关键节点播报（达成、超车、结束） | 可用 | 不需要实时读数时，这是最稳的 |

**测数值不要看 HUD**，一律用 `记入查看器`——它有毫秒级时间戳、无动效、可一键复制。

## `创建HUD文本` 的「重新赋值: 字符串」不会创建文本（2026-10-23 实测）

想在 HUD 上持续刷新，很容易写成「每 0.5 秒调一次 `创建HUD文本`，重新赋值选 `字符串`」——
结果游戏里**一个字都看不到**。`字符串` 的语义是「只把字符串写给已有文本」，没有就什么也不做。

实机实测（A2 诊断版，每 0.5 秒调一次 `创建HUD文本`）——结论比想象中麻烦：

| 写法 | 实机表现 |
|---|---|
| 只写 `重新赋值: 字符串`，从没建过 | 屏幕上**什么也没有** |
| 每帧 `可见和字符串` | 能看到，但**每次调用都新建一条**：`上一个文本ID` 一路 1 → 2 → 12 → 22 … |
| 先建一次再改用 `字符串` | **照样每次新建**（ID 继续涨到 122）——「原地更新」不成立 |
| 只建不删，ID 涨到 **128** | 之后 `上一个文本ID` 恒为 128，HUD 停更（**同时存在的 HUD 文本上限 128**） |
| 每次先 `消除HUD文本` 再建 | ID 继续 131 → 141 → … → **181**，完全没有 128 的限制 |

**128 限的是「同时有多少条 HUD 文本存活」，不是 ID 数字本身。**
ID 是只增不回收的计数器；只要每次删掉旧的，就只有 1 条存活，永远撞不到上限。
所以持续刷新必须**先删后建**：

```
While(真);
    消除HUD文本(事件玩家.hudId);                    // 先删旧的（首次为 0，无害）
    创建HUD文本(事件玩家, …, 可见和字符串, 默认可见度);
    事件玩家.hudId = 上一个文本ID;
    等待(0.5, 无视条件);
End;
```

（A3 探针已验完：ID **只增不回收**，128 限的是「同时有多少条存活」，见 E-32。）

所以持续刷新就一条路：**先删后建**（上面那段）。

**「建一次、之后只改文字」不成立**：同段 L313 的实测是——先建一次再改用 `重新赋值: 字符串`，照样每次新建（ID 一路涨到 122）。
别照那个写法抄，它没有任何读数支持。

校验器只在「整个文件从没用过 可见/可见和字符串」时才提示，正常套路不报。

`创建效果` 的 `重新赋值: 无` 则**是常规写法**（真实语料里大量出现、游戏能正常导入运行），
语义是「不覆盖已有效果」，不要当成错误——这条我们试过报提示，8 个语料里 3 个文件误报，已撤回。

## `创建HUD文本` 三个颜色留 `空` → 只剩一个半透明框（2026-10-23 实机）

A4 四组并排对照（同一玩家、同一时间创建四条文本）：

## 宣告胜利后规则不会自己停（2026-10-23 实机）

`宣告玩家胜利(玩家)` **是生效的**——比赛立刻进结算界面。结算前后**还会有几秒在跑规则**
（A8 实测：胜利那一秒心跳照发一条，3 秒后的下一条就没有了——也就是说整场比赛结束后规则都会停，
不是一直跑）。在那几秒里，`While(真)` 的循环可能再执行一轮，这就是「宣告胜利后又被触发一次」的来源。

`中断` 只结束**它所在的那条规则**，不会停别的规则的 `While(真)`。要干净收尾，仍然自己设守卫：

```
While(全局.ended == 假);          // 循环条件里带上状态
    …
End;

// 宣告胜利的地方
全局.ended = 真;
宣告玩家胜利(事件玩家);
```

或者让其它规则在结算页自行退出：

```
等待直到(游戏正在进行中() == 假, 999);
中断;
```

## 未开赛时 `伤害()` 不生效（2026-10-23 实测）

开赛前（英雄集结 / 倒计时阶段）调 `伤害(玩家, 来源, 10)`，掉血是 **0**，生命值一点不动。
所以任何「开局就动手」的规则，第一句都该是：

```
等待直到(游戏正在进行中(), 999);
```

否则前几秒的逻辑全是空跑，还会误导调试（日志显示打了伤害，血却没掉）。

## `设置最大生命值` / `设置移动速度` 的参数是百分比（2026-10-23 实测）

参数名就写着「生命百分比 / 移动速度百分比」——**100 = 原值**，不是绝对血量。

| 想要 | 写法 |
|---|---|
| 600 血英雄的一半血（300 点） | `设置最大生命值(事件玩家, 50)` |
| 原样 | `以下 100` |
| 2.1 倍 | `210`（语料里有这种写法） |

写 `300` 不会给 300 点血，而是 3 倍上限（1800），当前血还不变。
`ws.py check` 对 ≥250 的写法会出提示。

## 房间/英雄设置的系数会乘到 `伤害()` 上（实证：猪猪钩钩乐·原版）

大厅与英雄页里的「伤害量 / 受到伤害量 / 移动速度」这类百分比，**不是随便写写的装饰**，它会乘在运行时结果上，**包括工坊的 `伤害()` 动作**。

原版模式里的做法（`corpus/real/猪猪钩钩乐·原版.ow`）：

```
// 与英雄设置中的“伤害量 / 受到伤害量”保持一致，用于伤害动作补偿
全局.WorkshopCoreSettings[6] = 0.100;   // 房间造成伤害系数（英雄页写的是 10%）
全局.WorkshopCoreSettings[7] = 0.100;   // 房间受到伤害系数（同上）
全局.WorkshopCoreSettings[8] = 1 / (全局.WorkshopCoreSettings[6] * 全局.WorkshopCoreSettings[7]);

伤害(受伤玩家, 来源, 200 * 全局.WorkshopCoreSettings[8]);   // 乘回 100 倍，实际打 200
```

要点：

| 事实 | 说明 |
|---|---|
| 系数**会**作用到 `伤害()` 动作 | 所以 10% × 10% 的房间里，`伤害(…, 200)` 只打掉 2 点 |
| 两个系数是**相乘**关系 | `1 / (0.1 × 0.1) = 100`，作者用它把工坊伤害拉回原值 |
| 要跟自己写的房间数值**手动保持一致** | 房间改了 10% → 规则里的系数也得跟着改，否则补偿全错 |
| 改这些系数**不需要重进游戏**？ | 未实测，别假设 |

**英雄设置 × 规则动作 = 相乘，不是覆盖**（2026-10-23 实测，E-20）：

| 配置 | 打 100 实际掉血 |
|---|---|
| 英雄页 受到伤害量 200%，规则不设 | 200 |
| 英雄页 200% + 规则 `设置受到伤害(…, 50)` | **100**（100 × 0.5 × 2.0） |

结论：两边同时写时，实际倍率是**两个数相乘**，"规则覆盖英雄页"是错的直觉。
所以「英雄页调到 50%、规则里再调 50%」得到的是 **25%**，不是 50%。
`ws.py check` 对「两边都不是 100%」的组合会出一条提示，把乘积算给你看。

## 动作块末尾可以省 `End;`，但省了之后 `While` 只跑一次（2026-10-24 实测，E-61）

导入器**不拦**「少写一个 `End;`」。而且这不是笔误——导出文件里到处都是这么写的：
动作块的**最后一个** `If` / `While` 直接用结尾的 `}` 收尾。9 份真实语料里 5 份如此
（《暴打大锤3》《暴打大锤3.fixed》《猪猪钩钩乐·原版》《符文乱斗》《塔萨达练枪房》），
都是能正常玩的模式。

```
动作
{
    If(条件);
        ...做点事...
    Else;
        ...做别的事...
}          ← 这里没有 End;，合法
```

**但省掉 `End;` 会改变行为。** 探针 `tools/probes/lab/endcheck/endcheck-noend.ow`
是一条 `While(全局.A < 3);` 带两句动作、故意不写 `End;`：

| 观察 | 读数 |
|---|---|
| 导入 | **通过**，不报错 |
| 查看器 | `[00:00:08] [e1] A=1` —— **只有这一行** |
| 按写法应有的结果 | `A=1`、`A=2`、`A=3` 三行（同一秒，循环体内无等待） |

结论：**缺 `End;` 时循环体只执行一次就结束**（不是补齐、不是报错、不是死循环）。

**写法纪律**

- 自己写循环，`End;` 一个都别省；省了不报错，只是循环悄悄变成「做一次」。
- 看到别人的文件里循环只做了一次，先数 `End;`。
- 校验器只查**必要条件**：`check_loop_missing_end`（循环数 > `End;` 数才报，9 份语料 0 误报）。
  逐层配对那版分不清「故意省」和「忘了写」，真实语料上 5/9 误报，已按 D-006 撤回（见 `docs/validator-coverage.md`）。

## 自定义房间的时长上限：约 270 分钟（2026-10-31）

**一条事实**：自定义房间跑太久，服务器会把整局关掉、所有人被踢回大厅——不是「比赛结束」，是服务器直接关。
口径是 **约 270 分钟（4.5 小时）**，来自实际长时房间的经验值，不是官方文档写明的数字。

所以：按 270 分钟这个上限去规划，别设计成贴着上限硬撑。

**规避手法（只作参考，不是标准做法）**：确实见过有人在脚本里 `比赛时间暂停;` 冻住计时、
再按自己的节奏 `重新开始比赛;`，借此把一局拖过上限。但这类写法只是其中一种实现，
别人可能完全不这么写，也不代表必须这么写——要不要用看你的模式怎么设计。
